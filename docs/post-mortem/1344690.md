# AB#1344690

## Executive Summary

`auro-radio-group` marks itself invalid for screen reader users in the wrong place and without connecting the error message to the control. This work moves that "this is invalid" signal onto the actual grouping element inside the component, links it to the visible error text so assistive technology can read both together, and applies the same signal to each individual option in the group. Ticket: [AB#1344690](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1344690).

## The Problem

When a required radio group is submitted with nothing selected, it should tell screen reader users two things: that the group is invalid, and what the error message says. Before this fix, the "invalid" signal was attached to a part of the component that isn't the part assistive technology actually pays attention to, and the error message text had no formal link back to the group — so a screen reader could announce the error out loud once, but a user navigating with a screen reader afterward would not reliably hear that the group was invalid or be pointed at why.

## Root Cause

- `components/radio/src/auro-radio-group.js` renders the group's real semantics on a `<fieldset role="radiogroup">` inside its shadow DOM, but the invalid-state signal (`aria-invalid`) was imperatively set on the *custom element host* in `updated()` (`this.setAttribute('aria-invalid', 'true')`) — a different element than the one carrying `role="radiogroup"`.
- The error message rendered inside a versioned `auro-helptext` element with `role="alert" aria-live="assertive"`, which announces once when it appears, but had no `id`, and the fieldset had no `aria-describedby`/`aria-errormessage` pointing at it — so there was no durable, re-navigable link between the invalid control and its message.
- Individual `auro-radio` children received an `error` attribute for styling but no `aria-invalid` of their own.

## The Fix

- Removed the imperative `aria-invalid` set/remove on the host in `updated()`.
- Added a declarative `aria-invalid` binding directly on the `<fieldset>` in `render()`, using `ifDefined` so the attribute is present only when `validity` is not `'valid'` (mirroring the existing toggle semantics).
- Added `this.uniqueId` (via `UniqueId` from `@aurodesignsystem/auro-library`, following the same pattern already used in `base-input.js`), and wired `aria-describedby="${this.uniqueId}"` on the fieldset to `id="${this.uniqueId}"` on the help-text/error element (both render branches).
- Propagated `aria-invalid` to each `auro-radio` child alongside the existing `error` attribute, in the same `updated()` block.
- Updated the four existing WTR tests that asserted `aria-invalid` on the host to instead check the shadow-DOM fieldset, and added new tests for the `aria-describedby`/`id` association and per-radio `aria-invalid` sync.

## Why This Works

- `role` and `aria-invalid` now live on the same element (the fieldset), which is what makes the invalid state attributable to the actual group semantics rather than an unrelated ancestor.
- `aria-describedby` pointing at a stable `id` — rather than relying solely on a one-time live-region announcement — means a screen reader user can discover the error message any time they revisit the group, not just at the moment it first appears.
- Propagating `aria-invalid` to individual `auro-radio` children is safe specifically because `auro-radio`'s `role="radio"` reflects onto its own host element (confirmed by reading `auro-radio.js` before making this change) — so, unlike the group, there's no host-vs-shadow-DOM mismatch to repeat. This also guards against AT/browser combinations that only announce a container's `aria-invalid`/`aria-describedby` on initial entry (e.g. Tab) and not on every arrow-key move between radios.
- Both the fieldset and the help-text element live in the same shadow root, which was called out as a specific risk in the ticket ("must work within the same shadow root") — verified directly in the WTR test that resolves `aria-describedby` to an actual element via `shadowRoot.getElementById`.

## Outcome

The radio group's invalid state and error message are now expressed on the correct part of the component and linked together, so assistive technology has a durable way to convey both. As of the latest change on this branch, all 284 tests in the `auro-radio` package pass with 100% coverage, and lint is clean on the changed source file (pre-existing, unrelated lint warnings in the test file were confirmed unchanged via a baseline comparison).

## Follow-up Fix — Child State Desync

Recorded as its own section rather than folded into Root Cause / The Fix above, because the first commit's message cites line ranges inside those sections and editing them would invalidate an immutable reference. (Lesson noted in Learnings: cite headings, not line numbers.)

Code review of this branch found that the per-child `aria-invalid` introduced above created a *second* piece of per-child state that could drift out of sync with the existing `error` attribute.

**Root cause.** `handleItems()` re-mirrors group state onto children on every `slotchange` and on `connectedCallback`, but it only handled `error` — its last line was `el.error = Boolean(this.error)`. The clearing path for `aria-invalid` lived in `updated()` behind `changedProperties.has('validity')`, so it ran only when `validity` actually *changed*. For a group already invalid via `valueMissing`, `this.error` is `undefined`, so a slot change actively cleared `error` on every radio while `aria-invalid="true"` stayed behind — each radio rendered as visually valid while still announcing "invalid data" to assistive technology. The mirror case failed too: a radio slotted into an already-invalid group received neither attribute. Both are reachable from ordinary dynamically-rendered option lists and from detach/re-attach cycles.

**The fix.** Both attributes are now written together by a single private method, `syncItemValidity()`, called from both the `updated()` `validity` branch and `handleItems()`, so they cannot disagree regardless of which path runs.

**Coverage.** A regression test asserts that a radio slotted into an already-invalid group receives both attributes *and* that the radios already present keep theirs; it fails against the pre-fix source. An axe assertion on an invalid group pins the ARIA-attribute outcome for both the group-level and per-radio placement.

## Breaking Change Assessment

**Decision: not a breaking change. This ships as `fix` (PATCH) on `dev`.** Recorded explicitly because it is a judgment call rather than a mechanical one, and code review raised it on two separate passes.

What changed observably: `aria-invalid` was previously set imperatively on the `<auro-radio-group>` **host** element and is now set on the shadow-DOM `<fieldset>` and on each `auro-radio`. The host attribute is never set again. A consumer stylesheet rule such as `auro-radio-group[aria-invalid="true"] { … }`, or an end-to-end assertion on `auro-radio-group[aria-invalid]`, therefore stops matching silently, with no deprecation window. That cost is real and is the reason this section exists.

Reasons it is nonetheless treated as non-breaking:

- No public API surface changed. No attribute, property, method, event, or slot was added, removed, renamed, or re-typed. The `validity` property, the `error` attribute, and the visual presentation are all unchanged.
- The host attribute was never documented as public API. The accessibility page described these as `<fieldset>` attributes *before* this change, under the heading "The `<auro-radio-group>` element uses a `<fieldset>` with a `<legend>` internally."
- Setting ARIA state on an element that does not carry the corresponding `role` was precisely the defect being fixed. Keeping the host attribute for compatibility would mean keeping the bug.
- The ADO work item explicitly records "Breaking change: None — this corrects accessibility semantics; the public API and visual presentation are unchanged for existing consumers."
- An in-repo audit (`components/form/src`, `packages/`, `apps/`) found no reads of the host attribute outside the tests updated here.

Mitigation chosen in place of a MAJOR bump: the accessibility page now states that the attribute lives on the internal `<fieldset>` rather than the host, and directs consumers to target the `part="radio-group"` fieldset or read the `validity` property.

If this assessment is ever rejected, note that the consequence is not only a `BREAKING CHANGE:` footer and a MAJOR bump — repo policy routes intentional breakers to `breaking/formkit-v6` rather than `dev`, so the work would need retargeting.

Performed outside the session that produced the code fix, so per-pair observations are not captured here; no defects were reported back.

- **Playwright interaction/a11y tests cover the invalid-entry flow (focus/keyboard navigation of the group when invalid)** — five tests under the `── Invalid-group ARIA association (AB#1344690) ──` header in `apps/shared/accessibility-tree.suite.ts`, run against both the React and Svelte framework apps: fieldset-not-host placement, the `aria-describedby` association, per-radio `aria-invalid` when invalid, removal of `aria-invalid` when the group becomes valid, and retention of `aria-invalid` as arrow keys move focus between options. The last two close gaps found in code review — see the note below.
- **(Testing note) `components/radio/test/MANUAL_TESTING.md` gains a smoke step verifying a screen reader announces the invalid state and error message for a required radio group** — two steps added, plus a "Known/expected" callout documenting the intentional double "invalid data" utterance on Tab-in so a later reader does not "fix" it by removing the per-radio attribute.

**On the "keyboard navigation" half of the Playwright item.** The first pass satisfied only the *focus* half — invalidity was triggered through a real focus/blur cycle, but no test moved focus between radios while the group was invalid, which is the single behavior the per-radio mirroring exists to guarantee. Code review surfaced this and it is now closed by `radios keep aria-invalid as arrow keys move focus between options`.

That test has a wrinkle worth recording: arrow keys *select* in a radio group, so the first ArrowDown clears `valueMissing` outright — the invalid-and-arrowable state is only reachable via `customError`. The test therefore sets an `error` on the group, arrows from one radio to the next, and asserts the newly-focused radio still exposes `aria-invalid="true"`. A `valueMissing` group cannot be arrowed through while still invalid, which is itself useful to know.

Separately, the paired removal test previously asserted the attribute was absent on a fresh page, where it had never been set — it confirmed "never added" rather than "gets removed." It now drives the group invalid, asserts `aria-invalid="true"`, then selects an option and asserts the attribute is gone from both the child and the fieldset, so the removal path is genuinely exercised in a real browser.

**Risk that materialized:** the ticket's Risks section warned that "removing/adding `aria-invalid` must stay in sync with the existing `error`-attribute propagation to child radios so state doesn't diverge." That is precisely the defect the follow-up fix above addresses. The risk was written down before the work started, and the first pass still shipped it — the divergence had to be caught in code review rather than by heeding the ticket. Worth remembering the next time a Risks section names a specific failure mode. See [Follow-up Fix](#follow-up-fix--child-state-desync).

## Learnings

- When a component's ARIA `role` lives inside shadow DOM on a different element than the custom-element host (e.g. a `<fieldset role="radiogroup">`), state attributes like `aria-invalid` must be co-located with that element, not the host — check `role` placement before choosing where to bind related ARIA attributes.
- Before propagating an ARIA state attribute to child components, verify where *their* role lives too — `auro-radio`'s `role` reflects onto its own host, so it was safe to add `aria-invalid` there; a component that hides its role in shadow DOM (like the group itself) would need the same care applied recursively.
- `aria-describedby`/`id` association only works reliably when both elements share a shadow root — this was flagged as a risk in the ticket up front and was validated directly in a test rather than assumed.
- The identical bug pattern existed in a sibling component (`auro-checkbox-group`) with an *additional* variant (its `aria-invalid` was wired only to the `error` attribute, never to `validity`, so a required-and-empty group never showed an invalid state at all) — worth checking sibling/analogous components whenever fixing an ARIA placement bug, since the same authoring mistake tends to repeat.
- A demo/manual-test page built to make verification easy does not substitute for actually running that verification — the Playwright coverage and the `MANUAL_TESTING.md` steps landed with the fix, but the real-AT pass they exist to support had to be completed as a separate, deliberate follow-up after the code was written rather than alongside it.
- Do not cite post-mortem **line numbers** in a commit message. This commit's body pins "lines 11-16" and "lines 17-24", which froze those sections: the follow-up fix and the breaking-change rationale had to be appended as new sections below them rather than written where they belong, because a commit message is immutable and any insertion above would silently make it point at the wrong text. Cite the `## Heading` instead — it survives edits.
- Adding a second piece of per-child state means auditing *every* path that writes the first one. `aria-invalid` was added next to an existing `error` attribute but only in `updated()`, while `handleItems()` — the other writer, reached via `slotchange` and `connectedCallback` — kept writing `error` alone. The two then drifted. Consolidating both writes into one method keyed on one predicate is what actually fixes this class of bug, not adding the missing attribute to the second path.
- A tool built to make manual verification easier can itself introduce confusion if it conflates two independent actions in one control — the demo page's "Reset" button called both `removeAttribute('error')` and `reset()` together, which is what surfaced an apparent "reset a second time to fully clear" bug that turned out to be pre-existing, correct `valueMissing` behavior unrelated to this fix, not a defect in it.
