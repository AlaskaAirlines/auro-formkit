# AB#1344690

## Executive Summary

`auro-radio-group` marks itself invalid for screen reader users in the wrong place and without connecting the error message to the control. This work moves that "this is invalid" signal onto the actual grouping element inside the component, links it to the visible error text so assistive technology can read both together, and applies the same signal to each individual option in the group. Ticket: [AB#1344690](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1344690).

## The Problem

When a required radio group is submitted with nothing selected, it should tell screen reader users two things: that the group is invalid, and what the error message says. Before this fix, the "invalid" signal was attached to a part of the component that isn't the part assistive technology actually pays attention to, and the error message text had no formal link back to the group — so a screen reader could announce the error out loud once, but a user navigating with a screen reader afterward would not reliably hear that the group was invalid or be pointed at why.

## Root Cause

- `components/radio/src/auro-radio-group.js` renders the group's real semantics on a `<fieldset role="radiogroup">` inside its shadow DOM, but the invalid-state signal (`aria-invalid`) was imperatively set on the *custom element host* in `updated()` (`this.setAttribute('aria-invalid', 'true')`) — a different element than the one carrying `role="radiogroup"`.
- The error message rendered inside a versioned `auro-helptext` element with `role="alert" aria-live="assertive"`, which announces once when it appears, but had no `id`, and the fieldset had no `aria-describedby`/`aria-errormessage` pointing at it — so there was no durable, re-navigable link between the invalid control and its message.
- Individual `auro-radio` children received an `error` attribute for styling but no `aria-invalid` of their own.

## The Fix

- Removed the imperative `aria-invalid` set/remove on the host in `updated()`.
- Added a declarative `aria-invalid` binding directly on the `<fieldset>` in `render()`, using `ifDefined` so the attribute is present only when `validity` is not `'valid'` (mirroring the existing toggle semantics).
- Added `this.uniqueId` (via `UniqueId` from `@aurodesignsystem/auro-library`, following the same pattern already used in `base-input.js`), and wired `aria-describedby="${this.uniqueId}"` on the fieldset to `id="${this.uniqueId}"` on the help-text/error element (both render branches).
- Propagated `aria-invalid` to each `auro-radio` child alongside the existing `error` attribute, in the same `updated()` block.
- Updated the four existing WTR tests that asserted `aria-invalid` on the host to instead check the shadow-DOM fieldset, and added new tests for the `aria-describedby`/`id` association and per-radio `aria-invalid` sync.

## Why This Works

- `role` and `aria-invalid` now live on the same element (the fieldset), which is what makes the invalid state attributable to the actual group semantics rather than an unrelated ancestor.
- `aria-describedby` pointing at a stable `id` — rather than relying solely on a one-time live-region announcement — means a screen reader user can discover the error message any time they revisit the group, not just at the moment it first appears.
- Propagating `aria-invalid` to individual `auro-radio` children is safe specifically because `auro-radio`'s `role="radio"` reflects onto its own host element (confirmed by reading `auro-radio.js` before making this change) — so, unlike the group, there's no host-vs-shadow-DOM mismatch to repeat. This also guards against AT/browser combinations that only announce a container's `aria-invalid`/`aria-describedby` on initial entry (e.g. Tab) and not on every arrow-key move between radios.
- Both the fieldset and the help-text element live in the same shadow root, which was called out as a specific risk in the ticket ("must work within the same shadow root") — verified directly in the WTR test that resolves `aria-describedby` to an actual element via `shadowRoot.getElementById`.

## Outcome

The radio group's invalid state and error message are now expressed on the correct part of the component and linked together, so assistive technology has a durable way to convey both. All 280 tests in the `auro-radio` package pass with 100% coverage, and lint is clean on the changed source file (pre-existing, unrelated lint warnings in the test file were confirmed unchanged via a baseline comparison).

## Learnings

- When a component's ARIA `role` lives inside shadow DOM on a different element than the custom-element host (e.g. a `<fieldset role="radiogroup">`), state attributes like `aria-invalid` must be co-located with that element, not the host — check `role` placement before choosing where to bind related ARIA attributes.
- Before propagating an ARIA state attribute to child components, verify where *their* role lives too — `auro-radio`'s `role` reflects onto its own host, so it was safe to add `aria-invalid` there; a component that hides its role in shadow DOM (like the group itself) would need the same care applied recursively.
- `aria-describedby`/`id` association only works reliably when both elements share a shadow root — this was flagged as a risk in the ticket up front and was validated directly in a test rather than assumed.
- The identical bug pattern existed in a sibling component (`auro-checkbox-group`) with an *additional* variant (its `aria-invalid` was wired only to the `error` attribute, never to `validity`, so a required-and-empty group never showed an invalid state at all) — worth checking sibling/analogous components whenever fixing an ARIA placement bug, since the same authoring mistake tends to repeat.
- A demo/manual-test page built to make verification easy does not substitute for actually running that verification — the Playwright coverage and the `MANUAL_TESTING.md` steps landed with the fix, but the real-AT pass they exist to support had to be completed as a separate, deliberate follow-up after the code was written rather than alongside it.
- A tool built to make manual verification easier can itself introduce confusion if it conflates two independent actions in one control — the demo page's "Reset" button called both `removeAttribute('error')` and `reset()` together, which is what surfaced an apparent "reset a second time to fully clear" bug that turned out to be pre-existing, correct `valueMissing` behavior unrelated to this fix, not a defect in it.
