# AB#1594311

## Executive Summary

Four Alaska Airlines design system form components — Select, Combobox, Radio Group, and Checkbox Group — exposed a `noValidate` setting that was supposed to turn off automatic validation when a user leaves a field. The setting had no effect: these components validated the field every time focus left, regardless of whether `noValidate` was set. This produced a false error state (including an incorrect screen-reader announcement) for consumers who rely on deferred validation flows such as multi-step forms and wizard UIs. The fix makes all six form components consistently honor `noValidate` on blur, bringing the four broken components into alignment with how Input and Datepicker already worked.

## The Problem

When a consumer sets `noValidate` on a Select, Combobox, Radio Group, or Checkbox Group, they expect the component not to show a validation error when the user tabs away. Instead, the components ignored the setting entirely: every blur fired validation unconditionally, immediately marking a required empty field as invalid and announcing the error to screen readers. Consumers building multi-step forms, wizard flows, or applications that own their own validation lifecycle had no reliable way to defer inline validation on these four components.

---

## Root Cause

The shared `@aurodesignsystem/form-validation` library's `validate(elem, force)` method never reads `elem.noValidate` — it is a general-purpose validation runner, and the trigger policy belongs to each component. Two components (`auro-input` in `base-input.js` and `auro-datepicker`) correctly gate their blur handlers before calling `validate()`. The four broken components did not:

| Component | Blur trigger location | Issue |
|---|---|---|
| `auro-select` | blur listener in `connectedCallback` | Called `this.validate()` unconditionally |
| `auro-combobox` | focusout listener in `connectedCallback` | Called `this.validate()` without checking `noValidate` in its compound condition |
| `auro-radio-group` | `handleRadioBlur()` | Called `this.validation.validate(this)` unconditionally |
| `auro-checkbox-group` | `checkFocusWithin` closure in `firstUpdated` | Called `validation.validate(group)` unconditionally |

Two tests for the expected behavior were already written but commented out with `// This test fails due to a bug` notes in the select and combobox test files, acknowledging the bug. Radio and checkbox had tests that appeared to pass but did so vacuously because WTR's focus simulation did not reliably trigger those components' internal blur handlers.

---

## The Fix

Per-component `noValidate` guards were added to the blur/focusout handler in each of the four broken components, following the established pattern from `auro-input` and `auro-datepicker`:

- **`components/select/src/auro-select.js`** — wrapped `this.validate()` in `if (!this.noValidate)` inside the blur listener. The subsequent focus-state and typeahead-buffer cleanup remain unconditional.
- **`components/combobox/src/auro-combobox.js`** — prepended `!this.noValidate &&` to the existing compound focusout condition, short-circuiting before the more-expensive focus and dropdown state checks.
- **`components/radio/src/auro-radio-group.js`** — wrapped `this.validation.validate(this)` in `if (!this.noValidate)` inside `handleRadioBlur()`. `this.touched = true` is preserved unconditionally — interaction tracking is separate from validation.
- **`components/checkbox/src/auro-checkbox-group.js`** — extracted `document.auroCheckboxGroupActive` to a local `group` variable (removing repeated global property reads) and added `if (!group.noValidate)` before `group.validation.validate(group)`.

No changes to `@aurodesignsystem/form-validation`, `auro-input`, or `auro-datepicker`.

---

## Why This Works

The `validate()` library method operates as a runner: it enforces the triggering rules (touched state, focus, value presence) but does not own the decision of *when* to be called. Placing the `noValidate` check at each component's blur call site is consistent with this contract and with the two components that already worked correctly. The guard uses `!this.noValidate` rather than `this.noValidate === false` to handle the boolean property naturally.

The fix preserves all adjacent behavior:
- **Forced validation** (`validate(true)`) bypasses `noValidate` by design — the `force` flag signals an explicit programmatic call or form submission.
- **Selection-triggered validation** in radio (`handleSelection`) and checkbox (`handleValueUpdate`) passes `force = true` and is deliberately unaffected — validating on an explicit user selection is correct UX even when blur validation is suppressed.
- **`auro-form` integration** — the form's `submit()` calls `element.validate(true)` on all children regardless of `noValidate`, so required fields are still gated at submit time. A `noValidate` child's blur no longer fires `auroFormElement-validated`, so the form's validity state stays untouched during tabbing — which is the intended deferred-validation behavior.

---

## Outcome

Consumers who set `noValidate` on any of the six form components can now rely on consistent behavior: blurring a field will not produce an error state or screen-reader announcement until validation is explicitly triggered. Multi-step and wizard flows that defer validation until a submit action work correctly across all formkit form components.

## Learnings

- **Per-component trigger policy is the established contract in formkit.** The shared validation library is a runner, not a gatekeeper. Each component owns the decision of when to invoke `validate()`. This should be documented at the library level so future contributors know where noValidate guards belong.
- **Commented-out tests are a reliable signal of known bugs.** The two disabled select and combobox tests served as clear markers that the bug was known. When implementing a fix, always search for commented-out tests in the affected area before writing new ones.
- **WTR focus simulation gaps produce false-positive test passes.** Radio and checkbox had `noValidate` tests that appeared to pass, but only because the WTR environment did not trigger their internal blur handlers. The fix works in production; the tests were vacuous. For blur-path tests on web components, prefer custom event dispatch (`auroRadio-blur`) or direct method calls over relying on `document.body.focus()`.
- **`noValidate` must be distinguished from `force`.** The `force = true` flag on `validate()` is the correct mechanism for submit-triggered and programmatic validation — it should always bypass `noValidate`. Tests that verify `validate(true)` still runs when `noValidate` is set are as important as tests that verify blur is suppressed.
- **Form-level integration tests are a distinct layer.** Per-component WTR tests confirm the component behavior; the form integration tests confirm the boundary behavior (noValidate blur does not flip form state, submit still validates everything). Both layers are needed.

## Iterations That Didn't Work

**Central fix in `@aurodesignsystem/form-validation`** — Adding a `noValidate && !force` early return to `validate()` in the shared library was considered. It would have fixed all four components with one line. Rejected because the library's `validate()` is a general-purpose runner that should not own trigger policy; the per-component pattern used by `auro-input` and `auro-datepicker` is the established convention, and a library change would require regression testing every consumer.

**`document.body.focus()` for radio/checkbox blur simulation** — The initial regression tests for "required blur without noValidate still errors" used the same `r1.shadowRoot.querySelector('input').focus()` + `document.body.focus()` pattern as the existing noValidate tests. These failed because WTR does not reliably trigger the radio's `auroRadio-blur` custom event via this mechanism. Fixed by dispatching `auroRadio-blur` directly on the radio element (for radio) and by using `el.touched = true; el.validate()` (for checkbox, whose focus-leave handler is difficult to simulate in WTR).

**Host-level focus/blur for the form integration test** — The "does not update form validity when a noValidate child blurs" test initially used `input.focus()` / `input.blur()` on the `auro-input` host element. `handleBlur` in `auro-input` is wired via `@blur` in the Lit template on the shadow input, not the host, so host-level blur doesn't reach the handler. The WTR limitation is documented with a comment in the test, and the Playwright suite covers the real-browser path. A third assertion (`el.formState['city']?.validity`) was added to make the test meaningfully verify that no validation event was received by the form.
