# Post-Mortem: `activeLabel` on auro-input had no visual effect (AB#1494433)

**Issue:** AB#1494433

## Summary

`activeLabel` is a documented, reflected boolean attribute on `auro-input` intended to keep the label fixed in the active (raised, smaller) position at all times — even when the input is empty and unfocused. It had no visual effect: setting it left the label rendering in the default large placeholder position. The attribute reflected correctly to the DOM, so it passed a naive property/attribute test while doing nothing for users.

## What broke

Two problems combined to make the attribute a no-op:

1. The only place `activeLabel` was consumed was a bogus binding on the native `<input>`:

   ```js
   ?activeLabel="${this.activeLabel}"
   ```

   `activeLabel` is not a valid HTML attribute on `<input>`, so this rendered `activeLabel=""` on the native element and did nothing.

2. Nothing in the logic that actually decides label position/size looked at `activeLabel`. The "active label" appearance is not a single style — it is an emergent result of two getters:
   - `inputHidden` — when `true`, the native input row collapses (`util_displayHiddenVisually`) and the large label sits centered as a placeholder.
   - `labelFontClass` — returns `body-default` (large) in the empty/unfocused state, `body-xs` (small) otherwise.

   Both keyed off `hasValue`, `hasFocus`, and `placeholderStr` only. `activeLabel` was never part of the computation.

## Root cause

The attribute was defined, reflected, and documented, but was never wired into the label-positioning logic. The existing unit test only asserted attribute/property reflection (`el.hasAttribute('activeLabel')`), so the gap between "reflects" and "has a visual effect" was never caught.

## Fix

Treat `activeLabel` as an additional trigger of the active/raised state, composing with the existing `hasValue`/`hasFocus` logic, in the classic/default layout:

- `inputHidden` keeps the input row visible when `activeLabel` is set (classic/default only), so the label raises above it. This is folded into the empty/unfocused clause — gated on a shared `isClassicLayout` getter and `!activeLabelRaisesInput` — rather than a top-of-getter short-circuit, so the display-value clause used by combobox/datepicker is preserved.
- `labelFontClass` (classic branch) returns the small active font (`body-xs`) instead of the large placeholder font (`body-default`) when `activeLabel` is set.
- Added a shared private `isClassicLayout` getter (`!emphasized && !snowflake`) as the single source of truth for layout scoping, consumed by `inputHidden`.
- Added `activeLabel` to `commonWrapperClasses` as a greppable intent marker on the wrapper.
- Removed the no-op `?activeLabel` binding from the native `<input>`.

## Scope decision: classic/default only

The fix was intentionally limited to the classic/default layout. The emphasized and snowflake layouts always render the label inside the field (the large-centered → raised transition that `activeLabel` freezes does not exist there), so pinning the label adds no UX value. Rather than leave `activeLabel` a silent no-op on those layouts — the exact complaint that opened this ticket — the classic/default-only behavior is now documented in the property JSDoc and the customize docs so it is intentional and discoverable.

## Check

- Extended the WTR unit test beyond reflection to assert the **computed** rendered state on an empty, unfocused classic input: label uses `body-xs` (not `body-default`) and the input is visible (not `util_displayHiddenVisually`), with a baseline test confirming the default large position when `activeLabel` is unset.
- Written failing-first: confirmed the new assertions failed against the pre-fix code (490 passed / 2 failed), then passed after the fix.
- Added no-op tests for the emphasized and snowflake layouts (input stays hidden, label keeps its in-field size) to lock the classic/default scope. Final suite: 496 passed / 0 failed.

## Prevention

- When exposing a reflected attribute, assert its **rendered effect** (computed style / applied classes), not just attribute reflection — reflection tests pass on no-op attributes.
- Document layout-specific behavior explicitly so an intentionally-unsupported case doesn't read as a bug.
- When a change is meant to be layout-scoped, apply the scope through a **single shared condition** rather than repeating it per getter. The first pass here scoped `labelFontClass` to classic but left `inputHidden` unscoped, so `activeLabel` leaked into emphasized/snowflake. Code review caught it; **tests did not** — because the emphasized/snowflake cases weren't covered. Test every layout a shared getter feeds, not just the one you changed intentionally.
