# AB#1629494

## Executive Summary

A regression was introduced in the FormKit 6.1 release candidate where setting both the `error` attribute and the `noValidate` attribute on a form component caused the externally forced error to disappear the moment the user focused and then blurred away from the field. Any form that used `error` to surface server-side validation errors while also opting out of auto-validation (via `noValidate`) would silently lose those errors on first user interaction, giving users the incorrect impression that their input was accepted. The regression affected Select, Combobox, Radio Group, and Checkbox Group. The fix ensures that only auto-validation state is cleared on blur — externally forced errors survive untouched.

Related: [AB#1594311](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1594311) (the noValidate blur fix that introduced this regression)

---

## The Problem

When a consumer sets both `error="Some message"` and `noValidate` on a Select, Combobox, Radio Group, or Checkbox Group, the error state disappeared after the user focused the field and then blurred away. This was a regression from the 6.0 release, where `error` errors persisted correctly regardless of `noValidate`. Consumers using `noValidate` specifically to defer inline auto-validation — while still surfacing server-side errors via `error` — were silently broken in the 6.1 RC.

---

## Root Cause

The noValidate blur fix (AB#1594311) introduced stale-error-clearing logic: when `noValidate` is set and the user blurs, the component clears any `validity` state left behind by a previous `validate(true)` call (e.g. from form submission). This prevents stale errors from persisting indefinitely after the user re-interacts with a field.

The stale-clear `else if` branch did not distinguish between two types of validity state:

1. **Auto-validation state** — set by `validate(true)` (form submit) or `validate()` (blur trigger). Should be cleared on blur under `noValidate`.
2. **Externally forced state** — set by the `error` attribute. Should **never** be cleared by blur; the application controls when it appears and disappears.

Because the branch only checked `this.validity !== undefined`, it cleared both types indiscriminately. When a consumer set `error="Server rejected this value"`, the component entered `validity = 'customError'`. On the next blur, the stale-clear fired and reset `validity` to `undefined`, silently discarding the server error.

The affected components and their blur-handler locations:

| Component | File | Blur path |
|---|---|---|
| `auro-select` | `auro-select.js` | `connectedCallback` blur listener |
| `auro-combobox` | `auro-combobox.js` | `connectedCallback` focusout listener |
| `auro-radio-group` | `auro-radio-group.js` | `handleRadioBlur()` |
| `auro-checkbox-group` | `auro-checkbox-group.js` | `checkFocusWithin` closure |

---

## The Fix

Added `&& !this.error` (or `&& !group.error` for the checkbox closure) to the stale-clear `else if` condition in all four components:

```js
// Before
} else if (this.validity !== undefined) {
  this.validity = undefined;
  this.errorMessage = '';
}

// After
} else if (this.validity !== undefined && !this.error) {
  this.validity = undefined;
  this.errorMessage = '';
}
```

When the `error` attribute is present, the condition is false and the branch is skipped — the existing `customError` validity state survives the blur unchanged. When `error` is absent and the only validity state is from a previous `validate(true)` call, the stale-clear fires as intended.

A regression test was added to each component's `noValidate` describe block:

> *"should not clear error attribute state on blur when both error and noValidate are set"* — verifies that `validity` remains `'customError'` after blur when both attributes are set.

---

## Why This Works

The `error` attribute is an application-owned escape hatch: the consumer explicitly sets it to surface an error that did not come from the component's built-in validation (e.g. a server response, a cross-field constraint). Because the consumer controls when it appears, the consumer must also control when it disappears — the component must not touch it autonomously.

`validate(true)` errors, by contrast, are component-generated and tied to the form-submission cycle. The stale-clear is designed to remove those after the user re-interacts, so they do not outlast their usefulness. The distinction `&& !this.error` enforces exactly this boundary: auto-validation state is managed by the component; forced-error state is managed by the consumer.

---

## Outcome

With the fix applied, the two behaviors are independent and composable:

- `noValidate` + `error` — the `error` message persists through focus/blur cycles; the application removes it when it chooses.
- `noValidate` + a previous `validate(true)` error — the stale error is cleared on the next blur, giving the user a clean slate before the next submit.
- Without `noValidate` — blur validation runs normally; `error` state is still never cleared by the component.

## Learnings

- **Stale-clearing logic must distinguish error sources.** Clearing all validity state on blur is too broad — the `error` attribute is application-controlled and must not be touched by component-driven blur handlers. Any future stale-clear logic should carry the `!this.error` guard from day one.
- **Regression tests should cover attribute combinations, not just single attributes.** The `noValidate` test suite verified each attribute independently but missed the `error + noValidate` interaction. Combinatorial tests catch these silent conflicts before they reach an RC.
- **Error-state transitions belong to the owner of the error.** Auto-validation state is owned by the component; `error` attribute state is owned by the consumer. These must never be collapsed into a single code path that treats them identically.
