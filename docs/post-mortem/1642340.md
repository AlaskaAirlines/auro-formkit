# AB#1642340

## Executive Summary

A counter group's error state could silently disappear the moment a form was submitted — even while one of its counters still held an invalid value — letting the form go through as if everything were fine. This work makes the counter group correctly hold onto that error through submission, so a form containing an invalid counter is properly blocked until the value is corrected, matching how every other field type in the design system already behaves. Ticket: [AB#1642340](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1642340).

## The Problem

When one of the counters inside a counter group was in an error state — for example, too many passengers selected for the available seats — submitting the form made that error vanish. The counter group went back to looking normal and the form let the submission through, even though the counter itself was still wrong. Trying to validate again afterward didn't bring the error back either; it was simply lost. This was the only field type in the design system that behaved this way — every other field correctly kept its error visible through a form submission.

## Root Cause

- `packages/form-validation/src/validation.js`'s shared validator only recognizes `string`/`boolean`/`number`/`Array`-typed values when deciding whether an element "has a value." `auro-counter-group.value` is a plain object (a per-child value map built in `updateValue()`), so it's never treated as having a value, no matter what its children report.
- When forced validation runs (`auro-form.submit()` calls `element.validate(true)` on every registered field, including the group) and the group has no `error` attribute of its own, the shared validator unconditionally resets `elem.validity = 'valid'; elem.errorMessage = ''`. Because `hasValue` is always false for the group, none of the value-dependent branches that would otherwise re-derive validity ever run.
- `auro-counter-group.validate(force)` did nothing but delegate to that shared validator — it never re-applied the aggregation `updateValidity()` had built from the children. So the moment `validate(true)` ran, the group's correctly-aggregated invalid state was overwritten, and nothing brought it back on a later validation pass either, since nothing about the children had changed to re-trigger `updateValidity()`.
- A second, related defect on the same path: the aggregated `errorMessage` was built by calling `renderHelpTextErrors()`, which returned Lit `TemplateResult` objects rather than a string. Anything treating `errorMessage` as text rendered `[object Object]`.

## The Fix

- `components/counter/src/auro-counter-group.js`: extracted the child-aggregation logic into a synchronous private method, `computeValidityFromCounters()`.
- `validate(force)` now calls the shared validator as before, then — unless the group has its own `error` attribute, which still takes precedence exactly as it did before — immediately re-derives validity/errorMessage from the children's current state via that method. If the correction changes the outcome, it re-dispatches `auroFormElement-validated` so `auro-form`'s submit-time listener sees the corrected value instead of the one the shared validator just overwrote.
- Aggregated error messages are now joined into a plain, `'. '`-separated string instead of an array of Lit TemplateResults. `renderHelpTextErrors()`, which had no remaining call site once this changed, was removed along with its two now-orphaned unit tests.
- Caught by code review before this branch was pushed: the string-joining change initially kept the old code's `joinedMessage || this.errorMessage || undefined` fallback verbatim. That fallback was dead code under the old `TemplateResult`-returning method (an empty-messages call still produced a truthy, if empty-rendering, object), but became reachable once `errorMessage` became a plain string — a group transitioning from one invalid cause with a message to another with none of its own (e.g. a custom error to a plain range violation) would surface the *stale* message from the prior cause instead of clearing it. Fixed by dropping the fallback entirely, so the property always reflects the current invalid counters, never a previous cycle's leftover value.
- Ships as a non-breaking fix: no attribute, property, method, event, or slot contract changed. The only observable difference is that a previously-incorrect "valid" result is now correctly reported as "invalid" — a consumer relying on the old behavior to let an invalid counter group's form through was relying on a bug.

## Why This Works

- The fix lives entirely inside `auro-counter-group`, not the shared `AuroFormValidation` library. That library's `hasValue` semantics are relied on by several other components, and the ticket's own assessment called a fix "localized to one component."
- Guarding the re-derivation on `!this.hasAttribute('error')` means an error set on the group itself via the `error` **attribute** still wins and survives validation — the exact precedence the shared validator already implements, just re-applied on top of it. (`error` is declared `reflect: false`, so a group error set as a JS property rather than an attribute isn't covered by this guard — but that was already true of the shared validator's own `hasAttribute('error')` check before this fix, so it's a pre-existing, repo-wide limitation this change doesn't introduce or worsen.)
- Re-dispatching the validated event only when the corrected result actually differs from what the shared validator produced avoids sending `auro-form` a redundant event on every `validate()` call.
- The fix is ordering-independent: whichever settles first — a child's own validation completing before the group's forced `validate(true)` runs, or the reverse — the next re-derivation reads the children's live validity at call time. Children maintain their own validity independently of the group's forced-validate calls (only the group is registered with `auro-form` and receives `validate(true)`; children never do), so that live read is always accurate.
- The re-derivation intentionally runs on every `validate()` call, not just forced ones, even though this recomputes the same aggregation `updateValidity()`'s deferred path also computes a tick later for an ordinary child interaction. Scoping it to forced calls only was tried and reverted — see "Iterations That Didn't Work" below.

## Outcome

A counter group with an invalid counter now correctly blocks form submission and keeps showing its error after a blocked attempt, matching how every other field in the design system already behaves. The fix was verified with an expanded automated test suite (321 tests in the counter package, all passing), a real-browser test that submits an actual form and confirms it's blocked, and a visual check confirming the error styling stays visible after a submission attempt — all passing with no other functionality affected.

## Learnings

- A shared validation engine's type-based branching (checking a value's type to decide whether it "has a value") is a trap for any component whose value isn't one of the types the engine anticipates. `auro-counter-group`'s value is an object by design (a per-child value map), and the engine silently treated that as "no value" rather than erroring or falling back — the bug stayed invisible until forced validation specifically exercised the branch that assumes that check reflects reality.
- When a component layers its own aggregation logic (child state → group state) on top of a shared validator, a call into that shared validator can silently undo the aggregation unless the component re-applies it afterward.
- A property that other components render directly can absorb a non-string value without any visible error, because the rendering library is happy to render a list of render-objects inline — the defect only becomes visible where something *else* treats the same property as plain text.
- A `value || fallback` pattern's safety can depend entirely on the *type* of the thing it's guarding: a fallback that's unreachable under one return type (an always-truthy object) can silently activate the moment that type changes to something that's falsy when empty (a string), surfacing a staleness bug that was always latent in the logic. Caught by code review before the branch was pushed, not after.
- An "obvious" efficiency optimization — skipping a computation that looks redundant with a deferred one done elsewhere — can remove the only mechanism keeping two systems in sync, if the two code paths that look equivalent don't actually do the same thing (one sends a notification, the other doesn't). Caught by testing the change against the real behavior it affects, not just the unit tests for the method itself.

## Iterations That Didn't Work

Code review flagged that the re-derivation in `validate()` runs unconditionally, including on every unforced call — which happens on every child value change. That duplicates the aggregation `updateValidity()`'s deferred path already computes a tick later for the same event, and looked like pure wasted work.

**Attempted fix:** gate the re-derivation-and-redispatch block on `force`, so it only runs for the forced-validation scenario this ticket actually needed to fix, leaving ordinary interactive updates to the existing deferred path.

**Why it was reverted:** it broke `auro-form`'s submit-button-disabling on initial load. `updateValidity()`'s deferred path only ever updates the group's own validity/error-message properties — it has never re-dispatched the validated event, even before this ticket. Only `validate()`'s synchronous path notifies `auro-form` of a child-derived invalid state via that event. Gating it to `force` meant a counter group that's invalid from the moment it loads (before any submit attempt) correctly settled its own internal state, but `auro-form`'s tracked state never heard about it, so the submit button stayed incorrectly enabled — caught by the existing real-browser test, which checks the submit button is disabled *before* ever calling submit. The "duplicate" computation code review flagged is real, but only one of its two call sites actually notifies `auro-form` — removing the "redundant" one silently removed the only mechanism keeping the two in sync outside a forced validation. Reverted; the minor CPU cost of recomputing a small aggregation on each interaction was judged not worth carrying that risk for.
