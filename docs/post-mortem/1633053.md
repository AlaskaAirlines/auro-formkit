# AB#1633053

## Executive Summary

When developers build with Auro form components, their code editor offers help — autocomplete, hover descriptions, valid-value suggestions, and a strike-through when an option has been replaced by a newer one. That help is generated automatically from a single shared description of every component. Gaps and mistakes in that shared description were flowing straight through to every developer's editor: descriptions were missing, some suggested options didn't actually work, deprecated options weren't flagged, and in some cases the editor type definitions failed to build at all.

This change corrects and enriches that shared description across all Auro form components, so the editor help is accurate and complete and the generated type definitions build reliably. There is no change to how the components behave for people using them — this is purely an improvement to the developer experience.

See [AB#1633053](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1633053) in Azure DevOps.

## The Problem

The Auro CLI's editor targets — VS Code HTML custom-data and the JSX/Svelte type definitions — are pure transforms over each component's published Custom Elements Manifest (the shared machine-readable description of a component's attributes, events, slots, and parts). They can only surface what that manifest carries. Where autocomplete, hover docs, or value validation were weak, the gap was in the source manifest, not the tooling.

Concretely, developers saw: attributes with no descriptions; enumerated attributes offered as free-form strings instead of a fixed set of valid values; camelCase option names that the editor suggested but that never actually bound at runtime; deprecated options with no deprecation indicator; and, in the worst case, generated type definitions that would not compile — so the editor could offer no help for those components at all.

## Root Cause

The aggregate manifest is generated by the Custom Elements Manifest analyzer (`@custom-elements-manifest/analyzer`) from the components' source JSDoc and Lit property declarations, driven by `packages/config/src/custom-elements-manifest.config.mjs`. Several source-authoring patterns caused the analyzer to emit inaccurate metadata:

- **Constructor initializers overrode declared types.** Components assign enumerated properties a string literal in the constructor (e.g. `this.shape = 'classic'`), which made the analyzer infer `type.text: "string"` and discard the `@type` union declared in JSDoc — so `shape`, `size`, `layout`, `autocapitalize`, `autocorrect`, `spellcheck`, and `inputmode` surfaced as free-form strings.
- **camelCase attribute names.** Lit lowercases observed attribute names at runtime (`onDark` binds as `ondark`, `fullscreenBreakpoint` as `fullscreenbreakpoint`), but the manifest recorded the camelCase form, so the editor advertised an attribute name that never binds.
- **Missing descriptions and `@csspart` declarations** on attributes, events, classes, and rendered parts across the base classes (`components/layoutElement/src/auroElement.js`, `components/input/src/base-input.js`) and many components.
- **Malformed and inferred types.** The `auroDropdown-idAdded` event JSDoc in `components/dropdown/src/auro-dropdown.js` had an unbalanced `type.text` that the CLI's hardening dropped; `auro-menu` emitted a nameless member; and several members were inferred as bare `object`/`array`/`function`, which broke the generated `.d.ts` compilation.
- **Deprecation not flagged.** The analyzer emits the `deprecated` flag only from the explicit `@deprecated` tag, not from descriptive prose — so `onDark`, deprecated in favor of `appearance`, carried no deprecation indicator anywhere in the manifest.

## The Fix

All edits are behavior-preserving JSDoc / property-metadata changes across the components and their base classes, plus a regenerated `docs/api.md` for each affected component:

- **Typed enumerated attributes as closed string-literal unions**, rooted per-component so inherited types resolve correctly, and added inline `@type` above the constructor initializers (moving default assignments into helper methods where needed) so the analyzer preserves the union instead of inferring `string`.
- **Gave camelCase Lit properties explicit lowercase `attribute:` names** matching Lit's runtime binding (`onDark → ondark`, `fullscreenBreakpoint`, `autoPlacement`, etc.), correcting the manifest without changing any runtime binding.
- **Added missing descriptions** to attributes, events, and classes; **declared rendered parts** with `@csspart`; and documented the public `auro-menuoption` event attribute.
- **Fixed the malformed `auroDropdown-idAdded` `type.text`**, named the previously nameless `auro-menu` member, annotated members the analyzer had inferred as bare `object`/`array`/`function` with explicit `@type` shapes, and hid genuinely-private internal state (`hasAllValues`, `hasFocus`, `hasValue`, `hasTriggerContent`, `isPopoverVisible`) from the public attribute surface via `attribute: false`.
- **Added `@deprecated` to `onDark` everywhere it is superseded by `appearance`** (checkbox, checkbox-group, combobox, counter, counter-group, datepicker, dropdown, helptext, base-input/input, radio, radio-group, select) — 26 entries now carry the deprecated flag (was 0). `onDark` on `AuroElement`, `auro-menu`, and `auro-menuoption` is left intact, as those have no `appearance` replacement and remain the supported API.
- **Went beyond the ticket's documented limitation for events/slots.** The ticket noted that deprecated *events and slots* could not carry the flag in the current analyzer version. Rather than leave that gap, the config now consumes the shared `deprecatedProseToFieldPlugin` (extracted into `@aurodesignsystem/auro-library`, bumped to `^5.14.0`), which promotes deprecation prose on events and slots into the manifest `deprecated` field. The four deprecated events (`auro-checkbox` `change` and `auroCheckbox-input`, `auro-combobox` `auroCombobox-valueSet`, `auro-radio` `change`) were given explicit migration guidance the plugin extracts. That plugin extraction is tracked separately as AB#1633054.

## Why This Works

The editor tooling is a deterministic transform over the manifest, so correcting the source of that manifest fixes every downstream editor target at once. Each change targets the specific authoring pattern the analyzer misreads:

- Inline `@type` above the constructor assignment wins over the inferred literal, so the union survives regeneration — verified by regenerating `custom-elements.json` and confirming the union `type.text` is present rather than `"string"`.
- The explicit lowercase `attribute:` matches what Lit already observes at runtime, so the manifest now advertises the attribute that actually binds — the runtime behavior is unchanged, only the recorded name is corrected.
- Hiding internal state with `attribute: false` drops never-bound attributes from the public surface without affecting the property, so no consumer binding changes.
- The regenerated manifest is byte-equivalent between the local-plugin and shared-plugin approaches (verified by sorting modules by path and comparing), so adopting the shared plugin introduced no manifest drift.

## Outcome

- Developers now get accurate, complete editor assistance for Auro form components: correct autocomplete, helpful hover descriptions, valid-value suggestions for enumerated options, and a clear deprecation strike-through when an option has been replaced.
- The generated editor type definitions build reliably, so editors can offer help for every component instead of silently failing on the ones with broken types.
- Deprecated options — including the four deprecated events — now show a deprecation indicator with a migration hint, guiding developers toward the supported replacement.
- No change to how the components behave for end users; the only removals are never-bound internal attributes.

## Learnings

- The editor experience for a component is only as good as its manifest; when autocomplete/hover/validation is weak, fix the source JSDoc and property declarations, not the CLI.
- Constructor initializers silently override `@type` in the CEM analyzer — always add an inline `/** @type {...} */` above the assignment (or move defaults into a helper) and regenerate to confirm the union survives.
- Lit lowercases attribute names at runtime; a camelCase `attribute` name in the manifest advertises a binding that never fires. Give camelCase properties an explicit lowercase `attribute:`.
- The analyzer emits `deprecated` only from the `@deprecated` tag, and only for attributes/members — events and slots need a post-processing plugin to promote deprecation prose into the flag.
- Always regenerate `custom-elements.json` and diff it (normalizing non-deterministic module ordering) to prove a metadata change landed as intended and introduced no drift.
- A ticket's documented limitation is a floor, not a ceiling — extracting the prose plugin let this change flag deprecated events/slots that the ticket assumed could not be flagged.

## Iterations That Didn't Work

- **Bare deprecation flags on events.** The deprecated events were first set to a bare deprecated flag with no migration text, which the contract check rejected as `deprecated-no-detail`. Fixed by giving each event explicit `**DEPRECATED** - Use the \`input\` event instead.` prose (matching the datepicker `bib.fullscreen.dateLabel` slot convention) that the plugin extracts into a guidance message.
- **Keeping the prose plugin local.** The `deprecatedProseToFieldPlugin` was initially authored inline in `custom-elements-manifest.config.mjs`. Because every Auro component library needs the same capability, it was extracted into `@aurodesignsystem/auro-library` (AB#1633054) and consumed here instead, so the logic isn't duplicated and can't drift between repos.
