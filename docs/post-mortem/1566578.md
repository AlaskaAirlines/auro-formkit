# AB#1566578

## Executive Summary

Disabling a dropdown menu and then re-enabling it was accidentally re-enabling every option inside it — including any option that had been deliberately set up as unavailable on its own (for example, a sold-out fare class or an ineligible travel option). This work stops the menu from touching an option's own availability at all: toggling the whole menu off and back on no longer changes which individual options were already marked unavailable, while the menu as a whole still correctly looks and behaves as inactive while it's disabled. Ticket: [AB#1566578](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1566578).

## The Problem

A menu (the list of options behind things like a select dropdown) can be disabled as a whole, and individual options inside it can also be marked unavailable on their own. The bug: whenever the whole menu's disabled state was turned off, it forced every option back to "available" — even an option that was intentionally set up as unavailable. So a sold-out or ineligible choice could reappear as selectable simply because the surrounding menu was re-enabled, with no connection to whether that specific option should actually be available again.

## Root Cause

- `components/menu/src/auro-menu.js`'s `updateItemsState()` contained an unconditional mutation: whenever the menu's `disabled` property changed, it looped over every child option and set `option.disabled = this.disabled`. Toggling the menu `disabled` → `true` → `false` therefore force-enabled every option, clobbering any option authored with `disabled` in markup.
- Git history shows this was never an intentional design: the propagation has existed since the very first commit that added `auro-menu` (`2fe16fdc8e`, "feat: add menu #28"), predating multi-select, the v5.9 context-based rewrite, and the v6 rewrite that replaced it. The pre-revert v5.9/v5.12 implementation (`auro-menu.context.js` + `AuroMenuOption.handleMenuChange()`) had the identical defect — it blindly applied `this[event.property] = event.value` for any menu property the menu broadcast, including `disabled` — so there was no earlier "smarter" version of this logic to restore. It reads as "disable the menu" having been implemented as "blast `disabled` onto every child," without anticipating a child that already had its own `disabled`.
- Removing the mutation outright exposed two gaps it had been accidentally covering: keyboard navigation/selection had no other guard against a disabled menu (`navigateOptions()` and `makeSelection()` didn't check `this.disabled`), and there was no visual treatment for a disabled menu's options other than the mutation itself.
- A code-review pass surfaced a third, narrower gap in the fix itself: because the old mutation ran on *whichever* `auro-menu` instance's own `disabled` changed — including a nested submenu, since each instance's `this.items` is a deep query over its own descendants — disabling a nested submenu **directly** (not the root) used to disable its options for keyboard purposes too. Root-level keyboard handling (`navigateOptions()`/`makeSelection()`) only ever checks the *root* menu's own `this.disabled`, so once the mutation was removed, a directly-disabled nested submenu's options stayed keyboard-reachable even though they were visually and pointer-wise correctly inert. The same gap existed in `isSelectableByValue()` (used for programmatic `value=` assignment), which also only checked the option's own attributes.
- A second code-review pass on that fix caught two more issues: the CSS visual treatment (below) didn't actually cover a *selected* option's text/icon color, and the new Storybook example (below) was added as a loose HTML/JS pair but never wired into this package's Storybook export list, so it silently never rendered.
- A third code-review pass on the fix-for-the-fix caught two more: switching the CSS to `::slotted()` (to win over a selected option's local color) only reaches options *directly* slotted into whichever menu is disabled — a nested submenu's own options, one shadow tree further in, are outside that `::slotted()`'s reach, so disabling the *root* stopped visually dimming a nested submenu's options even though it correctly blocks their interactivity. Separately, `auro-select`/`auro-combobox` each independently reimplement their own "is this option available" checks — `auro-menuoption.isActive`, `auro-combobox`'s `activateFirstEnabledAvailableOption()`/`activateLastEnabledAvailableOption()`, and `auro-select`'s `getEnabledOptions()` — none of which were touched by the ancestor-chain fix in `auro-menu-utils.js`, so a disabled nested submenu's options could still be keyboard-activated through those separate paths even though `auro-menu`'s own navigation correctly skips them.
- A fourth code-review pass caught two accessibility/robustness gaps left by removing the original mutation: (1) `auro-menuoption`'s `aria-disabled` is only ever set reactively from its *own* `disabled` property changing (`updated()` in `auro-menuoption.js`); since the menu never writes that property anymore, an option with no authored `disabled` never got `aria-disabled` announced while its menu was disabled — screen reader users would hear every option as a normal, selectable item with no indication the menu was unavailable. Unlike the interactivity checks (which can be computed lazily at the moment of interaction), ARIA state has to be pushed onto the DOM proactively, since assistive tech reads the attribute directly rather than calling a getter. (2) `handleOptionHover()` had no disabled/ancestor-disabled guard at all — it relied entirely on the CSS `pointer-events: none` rule to keep a real hover from ever reaching a disabled-ancestor option, so any path that doesn't go through pointer hit-testing (a synthetic `mouseover` dispatch, test automation, or a future CSS change) could still highlight an option inside a disabled menu.
- A fifth code-review pass caught a bug in the fourth pass's own `aria-disabled` fix: the push logic ran inside `updateItemsState()`'s per-item loop over `this.items`, which (same as the original bug) is a **deep** query spanning nested submenus. The *set* branch is harmless being deep (announcing "disabled" on an already-disabled descendant is correct either way), but the *clear* branch only checked the option's own authored `disabled`, not whether any ancestor menu was still disabled — so re-enabling an unrelated **root** menu would incorrectly strip `aria-disabled` from a **nested submenu's** options even while that submenu was still independently disabled and still functionally inert. A screen reader would then report those options as available again, even though clicking/selecting them still silently did nothing.

## The Fix

- `components/menu/src/auro-menu.js`: removed the `option.disabled = this.disabled` mutation from `updateItemsState()` entirely — the menu never writes to an option's own `disabled` property or attribute, in either direction.
- Added a `this.disabled` early-return guard to both `navigateOptions()` and `makeSelection()`. `auro-select` and `auro-combobox` call `menu.makeSelection()` directly from their own keyboard strategies, bypassing the menu's internal keydown handler, so the guard lives inside `makeSelection()` itself rather than only at the keydown entry point — covering Arrow-key navigation, Enter, Tab-triggered selection, and any direct external caller uniformly.
- `components/menu/src/styles/default/style-menu.scss`: added `pointer-events: none` on the menu's option wrapper when `:host([disabled])`, blocking pointer hit-testing (clicks and hover highlighting) on the whole option list from the menu's own stylesheet.
- `components/menu/src/styles/default/color-menu.scss`: `:host([disabled])` now carries **two** declarations of the same colors (`--ds-auro-menuoption-container-color`, `--ds-auro-menuoption-text-color`, `--ds-auro-menuoption-icon-color`), each covering a need the other can't: a bare, plain-inheritance declaration (no `!important`, no `::slotted()`) that reaches a nested submenu's options through arbitrarily many shadow-tree boundaries since inheritance always crosses them; and a `::slotted(auro-menuoption)`/`::slotted([auro-menuoption])` declaration **with** `!important`, scoped to this host's own direct option children, that wins over a selected/active option's local color (inheritance alone can't — see Why This Works). No option *attribute* is written either way.
- `components/menu/src/auro-menu-utils.js`: `isOptionInteractive()`, `isSelectableByValue()`, and (exported for reuse) `hasDisabledAncestorMenu()` itself all walk up an option's ancestor-menu chain (root and any nested submenus) and treat the option as non-interactive/non-selectable if *any* ancestor menu is disabled — closing the nested-submenu gap for keyboard/pointer interaction *and* programmatic `value=` assignment, without reintroducing any mutation (a check performed at interaction/resolution time, not a write).
- `components/menu/src/auro-menuoption.js`: the `isActive` getter (consumed by `auro-select`'s `getActiveOptions()` for type-ahead navigation) now also calls `hasDisabledAncestorMenu()`, imported from `auro-menu-utils.js` — the one place that import crosses files, since both live in the same package.
- `components/combobox/src/auro-combobox.js` and `components/select/src/selectUtils.js`: `auro-combobox` and `auro-select` each only ever talk to `auro-menu` through its public DOM contract (`.options`, `.disabled`, `option.isActive`, etc.) — neither package imports `auro-menu`'s internal module, by existing convention (confirmed: neither lists `auro-menu` as a dependency, and neither previously imported from it). So each gets its own small, duplicated `isOptionOrAncestorMenuDisabled()`/ancestor-walk, matching the same logic as `hasDisabledAncestorMenu()` rather than importing it: added to `activateFirstEnabledAvailableOption()`/`activateLastEnabledAvailableOption()` in combobox (both actively used, called from `comboboxKeyboardStrategy.js`), and to `getEnabledOptions()` in select (currently unused in production, fixed anyway for consistency with its own test suite's stated contract).
- `components/menu/test/auro-menu.test.js`, `components/select/test/selectUtils.test.js`, `components/combobox/test/auro-combobox.test.js`: added coverage for authored-disabled preservation across menu disable/enable toggles; the no-mutation guarantee on non-authored options, including in `multiSelect` mode; keyboard navigation/selection being blocked while the menu itself is disabled; a directly-disabled nested submenu's options being skipped by root keyboard navigation, rejected by `makeSelection()`, rejected by programmatic `value=` assignment, excluded from `isActive`/`getEnabledOptions()`, and skipped by combobox's `activateFirstEnabledAvailableOption()`; and that an already keyboard-highlighted option's active state is left untouched by a disabled toggle. (`auro-menuoption.test.js`'s own `isActive` ancestor-disabled case was ultimately written into `auro-menu.test.js` instead, to stay under that file's 300-line ceiling — see Learnings.)
- `components/menu/apiExamples/disabled-menu-toggle.html` / `.js`: added a Storybook example (wired into `individual-api-examples.stories.ts`'s generated export list — see below) showing a menu with one pre-selected option and one pre-authored-disabled option (a "sold out" fare class) and a button that toggles the whole menu's `disabled` — making the preserved-authored-disabled contract, and the selected-option-still-dims-correctly fix, visible to consumers, not just covered by unit tests.
- `components/menu/stories/individual-api-examples.stories.ts`: this package's story files are glob-discovered from `apiExamples/*.html`+`.js` but each one still needs an explicit `export const <Name> = stories.<Name>;` line (there is no fully-automatic registration) — added `export const DisabledMenuToggle = stories.DisabledMenuToggle;`, without which the new example above was silently never rendered.
- `components/menu/src/auro-menu.js`'s `updateItemsState()`: added an `aria-disabled` push, scoped to the `disabled`-change branch — sets `aria-disabled="true"` on every item when `this.disabled` becomes true, and clears it on re-enable *only* for options that aren't themselves authored `disabled` **and** have no other disabled ancestor menu in their chain (`!option.disabled && !hasDisabledAncestorMenu(option)`) — the same ancestor-chain helper already used by `isOptionInteractive()`/`isSelectableByValue()`/`isActive`, imported here too. This writes a different attribute than the original bug's mutation (`aria-disabled`, not `disabled`), guarded the same way the CSS and JS checks are, so it doesn't reintroduce the clobbering this ticket fixes — including the nested-submenu variant of it caught by the fifth review pass.
- `handleOptionHover()` in `auro-menu.js`: added an `isOptionInteractive()` early return, matching the guard already present in `makeSelection()`, so hovering a disabled-ancestor option can never activate it regardless of how the hover was triggered.

## Why This Works

- The CSS now needs two declarations because inheritance and `::slotted()` solve opposite halves of the problem, and neither alone solves both. Inheritance crosses every shadow boundary it encounters, no matter how deep the submenu nesting goes — which is exactly why it's needed for the nested-submenu-visual-reach gap — but an inherited value can never outrank *any* local declaration on the element that receives it, no matter its specificity or `!important`, because inheritance is strictly the last-resort fallback in the cascade; it structurally cannot win a fight it was never entered into. `::slotted()` is the opposite: it declares a value *directly on the slotted option element* — a genuine local declaration from the ancestor's perspective — so it genuinely competes in the same cascade as the option's own `:host([selected])`/`:host([selected].active)` rules, and with `!important` it wins that fight regardless of the option's own specificity. But `::slotted()` only ever reaches a host's *own* direct slotted children, never through a second shadow tree into a nested submenu's own options — hence needing inheritance too.
- The residual gap this leaves (documented in the CSS source comment): a selected-but-not-individually-disabled option nested inside a submenu that is itself not disabled, while only an ancestor like the root is disabled, only receives the inherited declaration (its own submenu's `::slotted()` rule isn't active, since that submenu isn't the one with `disabled`) — so it keeps its accent color instead of fully dimming. It's still fully inert (the JS ancestor-chain check blocks interaction regardless of any CSS); this is accepted as a narrow, cosmetic-only limitation rather than chased further, since fully closing it would mean propagating something down to nested `<auro-menu>` elements — reopening the same design question as the rejected `menuDisabled` attribute, just at the menu-to-menu level instead of menu-to-option.
- An option that *is* authored `disabled` is unaffected in practice (even though the ancestor's `!important` rule technically "wins" over the option's own non-`!important` `:host([disabled])` rule) because both declare the identical color values — whichever one the browser picks, the rendered result is the same.
- Guarding `makeSelection()` and `navigateOptions()` directly (not just the menu's own `handleKeyDown`) was necessary, not optional: `auro-select`'s and `auro-combobox`'s keyboard strategies call `menu.makeSelection()` directly, so a guard placed only at the keydown layer would have left those call paths unprotected.
- Those two guards check `this.disabled` (the *root* menu's own state), which correctly blocks everything when the root is disabled, but can't see a *nested* submenu's own `disabled` — keyboard handling always runs on the root. `isOptionInteractive()`/`isSelectableByValue()`'s shared ancestor-chain check is evaluated per-option at the moment of the interaction (navigation skip, selection attempt, value resolution), so it correctly reflects whichever menu in the chain — root or any nested submenu — actually owns that specific option, without the root ever needing to know about a nested submenu's state.
- That same ancestor-chain logic had to be duplicated, not shared, into `auro-combobox` and `auro-select` — both packages only ever address `auro-menu` through its public DOM contract today (no existing import of `auro-menu`'s internal module from either), and introducing a new cross-package module dependency just for this one helper would be a bigger architectural change than the bug warrants. `auro-menuoption.isActive`, by contrast, legitimately imports from `auro-menu-utils.js` because both files already live in the same package.
- Mouse-click selection was already independently blocked via an existing `this.disabled` check in `handleMouseSelect()`, predating this fix — the `pointer-events: none` rule is a visual/hover reinforcement of behavior that was already functionally correct, not a new functional gate.
- An initial design alternative — adding a second, menu-owned `menuDisabled`/`menu-disabled` property+attribute directly on `auro-menuoption`, separate from its own `disabled` — was considered and rejected (see "Iterations That Didn't Work") in favor of this CSS-only, no-new-attribute approach, which was confirmed to still satisfy every behavior the ticket asked for. The nested-submenu gap reinforces why: propagating `disabled` down to nested `<auro-menu>` elements (mirroring how `noCheckmark`/`size`/`shape` already propagate) was also considered as the fix for that gap, but rejected for the same reason as the original mutation — it would silently clobber an authored `disabled` on a nested submenu, just one level up from where the original bug lived. The ancestor-chain *check*, shared/duplicated across `isOptionInteractive()`, `isSelectableByValue()`, `isActive`, and the combobox/select equivalents, gets the same correctness without writing to anything.
- The `aria-disabled` push is the one place this fix *does* write something onto the option from the menu — deliberately, and safely, because it targets a different attribute than the one the bug was about. `aria-disabled` isn't read by any of this fix's own interactivity logic (that's all `isOptionInteractive()`/ancestor-chain-based); it exists purely for assistive tech, which reads attributes directly off the DOM rather than calling a getter, so unlike every other piece of state in this fix it genuinely cannot be resolved lazily at interaction time — it has to be pushed. The guard on the clearing branch (`!option.disabled && !hasDisabledAncestorMenu(option)`) is what keeps this from becoming a second version of the original bug: it only clears an `aria-disabled` the *menu* set, never one the option's own `updated()` set for its own authored `disabled`, and — since the fifth review pass — never one a *different*, still-disabled ancestor menu is independently responsible for. The first version of this guard only checked the option's own `disabled`, missing that `this.items` is a deep query: toggling an unrelated root back on would otherwise walk straight past a nested submenu's own options and clear an `aria-disabled` that submenu still needs.

## Outcome

A menu that's turned off and back on no longer changes which of its individual options were already set up as unavailable — only the menu's own on/off state is affected, at every level of nesting and for every way an option could be selected (click, keyboard, hover, or a consumer setting a value in code) — including when that interaction is driven by `auro-select` or `auro-combobox` rather than the menu itself. While the whole menu (or a nested group within it) is off, every option inside it correctly behaves as inactive (not clickable, not reachable by keyboard, hover, or type-ahead), is correctly announced to screen readers as unavailable **for as long as it's actually inert — including a nested submenu's options surviving an unrelated ancestor's re-enable** — and — with one narrow, documented cosmetic exception for a selected option nested two or more menu levels below the one that's actually disabled — visually dims too, and turning it back on correctly restores each option to exactly the availability it had before. The behavior is now also demonstrated in Storybook, not just covered by unit tests. Verified with an expanded automated test suite in the menu package (532 tests, all passing) plus the menu-option, select (578), and combobox (526) suites, since both of those components drive menu selection directly — all passing with no other functionality affected. (A single, pre-existing, intermittent timing flake in one unrelated `auro-combobox` popover-visibility test was observed early on and confirmed unrelated — it fails and passes identically across reruns with no code changes in between; it did not reproduce in the final verification pass.) Five successive code-review passes over this change, in addition to the automated suite, each surfaced a real additional gap before merge — documented in this post-mortem's Root Cause, Why This Works, and Iterations sections.

## Ticket Completeness

9 of 9 decomposed requirements resolved (the ticket's Description and Acceptance Criteria fields were empty; requirements were decomposed from the "Desired behavior" paragraph in its Repro Steps field).

**Resolved:**
- `auro-menu` no longer propagates or mutates option-level `disabled` — the mutating line was deleted outright, with a dedicated test confirming no option is ever written to.
- Options inside a disabled menu still render — unaffected, no rendering logic was touched.
- Options are not focusable while the menu is disabled — options were already permanently `tabIndex="-1"` and never natively focusable, independent of disabled state; unaffected by this change.
- Options are skipped by keyboard navigation while the menu is disabled — `navigateOptions()` now returns early on `this.disabled`, covered by a dedicated test.
- Options are not selectable/activatable via pointer while the menu is disabled — already blocked via `handleMouseSelect()`'s pre-existing `this.disabled` check; reinforced visually with `pointer-events: none`.
- Options are not selectable/activatable via Enter while the menu is disabled — `makeSelection()` now returns early on `this.disabled`, covered by a dedicated test, including the direct-call path used by `auro-select`/`auro-combobox`.
- Options are visually disabled while the menu is disabled, including ones that are currently selected or keyboard-active — achieved via `!important` CSS custom properties declared on the slotted options from the menu's own `:host([disabled])` stylesheet (via `::slotted()`), with no option attribute written.
- The fix does not write `disabled` onto each option — confirmed by a dedicated "never write `disabled`" test and by code review of the diff.
- Authored option-level `disabled` is preserved across menu enable/disable toggles — covered by a dedicated test asserting the authored-disabled option's state is unchanged through a full disable→enable cycle.

The ticket's own repro steps describe a flat option list and don't mention assistive tech or hover explicitly; five code-review passes additionally surfaced, and this change additionally fixes, related gaps outside that literal scope: a nested submenu disabled directly (not the root) is now also correctly keyboard-inert and rejects programmatic value selection; a selected option now correctly dims instead of keeping its accent highlight while disabled (except for the narrow nested+selected+only-ancestor-disabled case noted in Why This Works); `auro-select`'s and `auro-combobox`'s own independent "is this option available" checks now agree with `auro-menu`'s; options are now correctly announced as `aria-disabled` to assistive tech while the menu is disabled, restoring behavior the original mutation happened to provide as a side effect, **and correctly keep that announcement when a nested submenu stays independently disabled while an unrelated ancestor re-enables**; a hover-triggered activation path that bypassed the CSS pointer-events guard is now also blocked at the JS level; and the Storybook example demonstrating all of this is now actually wired up to render. All with dedicated tests except the Storybook wiring itself, which was caught by code review reading the stories file directly — Storybook examples aren't covered by this package's automated test suite.

## Learnings

- When a piece of behavior looks intentional (it's been in the codebase since the component's first commit), check whether it was actually load-bearing before preserving it — git archaeology here showed the "same" bug existed in two independent implementations across two major rewrites, which is good evidence it was never a deliberate design, just an unexamined default.
- Deleting a mutation that was "silently" covering other requirements (here: keyboard blocking, visual disabling) can regress those requirements even though removing the mutation is correct — always trace what else currently depends on the code being removed before deleting it.
- A method called only from a component's own internal event handler can still be a public integration point for other components (`auro-select`/`auro-combobox` call `auro-menu.makeSelection()` directly) — guards belong in the method itself, not just at the handler that happens to be the component's own entry point.
- CSS custom properties crossing the shadow boundary from an ancestor's `::slotted()` rule (not via `::part()` or explicit JS prop-passing) is a reusable pattern for "parent visually influences child" without the parent ever touching the child's actual state/attributes — useful whenever a container needs to express a state its children should reflect without claiming ownership of the children's own properties.
- Inheritance and `::slotted()` solve two different problems and aren't interchangeable, even though both can set a custom property "from the outside": inheritance can only supply a *fallback* a child is always free to override locally — useful when the parent's state should apply only in the absence of the child's own opinion — while `::slotted()` places a real, locally-competing declaration directly on the child, which is required whenever the parent's state must win *even over* a child's own existing local declaration. Picking inheritance for this fix initially (because it elegantly solved the *authored-disabled* case) didn't account for the *selected*/*active* cases needing the opposite guarantee — the parent overriding, not deferring to, the child's local style.
- A multi-level component tree (root menu → nested submenu → options) means "the thing that owns keyboard handling" and "the thing whose own state should gate interactivity" aren't always the same instance. A guard on the method that owns the interaction (`this.disabled` in the root's `navigateOptions()`/`makeSelection()`) only protects against *that instance's* own state; a check that needs to honor state anywhere in an ancestor chain has to actually walk that chain, not assume the direct caller is the only relevant instance. This applies uniformly to every way an option can become selected — keyboard, pointer, and programmatic `value=` assignment all needed the same ancestor-chain check; fixing only the keyboard/pointer path and missing the programmatic one was caught in a follow-up review pass specifically because it's a separate code path (`isSelectableByValue()`) that happened not to be touched by the first round of fixes.
- Generated/glob-discovered registration (this package's Storybook stories) can still have a manual step hiding behind the automation — here, an explicit `export const <Name> = stories.<Name>;` line per example — that's easy to assume is automatic and skip, with no error or test failure signaling the omission (the example still compiles and sits in the generated `stories` object; it's simply never exported, hence never rendered). Worth greping for the sibling exports' pattern before assuming a new generated-content file is "just picked up."
- `::slotted()` and inheritance aren't substitutes for each other even though both "reach into" a shadow tree from outside — `::slotted()` only ever matches a host's own *direct* light-DOM children, never through a second slot/shadow-tree boundary into a nested custom element's own content, while inheritance keeps propagating through however many shadow boundaries it meets. A fix that needs to reach an arbitrarily-nested tree *and* override local declarations needs both declared together, not a choice between them — something that only became apparent once "nested submenus" entered scope at all, which the original flat-list ticket never mentioned.
- A single shared "is this interactive" check living in one file doesn't guarantee every consumer of a concept queries it — `auro-menuoption.isActive`, `auro-combobox`'s own activate-first/last-option logic, and `auro-select`'s `getEnabledOptions()` all independently re-express "is this option available," and fixing the canonical one (`auro-menu-utils.js`) silently left three siblings behind. Worth greping for a concept's *other names* (`.disabled`, `isActive`, `isEnabled`, `available`) across sibling packages, not just the function literally being changed.
- Respecting an established architectural boundary (here: `auro-select`/`auro-combobox` never importing `auro-menu`'s internal module, only its public DOM surface) sometimes means accepting duplicated logic across packages rather than introducing a new dependency to deduplicate it — the three-line ancestor-walk repeated in `auro-menu-utils.js`, `auro-combobox.js`, and `selectUtils.js` is a deliberate trade, not an oversight.
- Not every piece of derived state can be resolved lazily. Removing a mutation in favor of an on-demand check (`isOptionInteractive()`, computed only when a navigation/selection attempt actually happens) is the right general pattern here, but it silently doesn't cover state that something *outside* the component's own control loop reads directly and asynchronously — assistive tech reads `aria-*` attributes off the live DOM whenever it chooses, not by calling into the component's logic at a moment the component controls. That category of state still has to be pushed proactively, with the same non-clobbering guard discipline as everything else in this fix.
- A CSS-only interaction guard (`pointer-events: none`) is a real defense, but it only covers the one input channel it's built for (genuine pointer hit-testing). Any JS path that produces the same event through a different mechanism — a synthetic dispatch, a different event source, test automation — walks right around it. Where a fix's stated goal is "no exceptions," every code path that can reach the guarded behavior needs its own check, not just the most common one.
- "`this.items` is a deep query spanning nested submenus" turned out to be the single root fact worth re-checking on *every* new piece of logic added to `updateItemsState()`'s per-item loop in this fix — it's exactly what made the original mutation bug possible, and the `aria-disabled` push (added specifically *to fix* a gap from removing that mutation) fell into the identical trap one more time: a deep loop plus a guard that only consults the current option's own state, with no thought for whether a *different* ancestor in the chain still has an opinion. The fifth review pass caught it because it asked the same question of the newest code that the first review pass had asked of the original code — "what if this option belongs to a nested menu, not the one whose property just changed?" — a question worth asking by rote of any loop over a deep-query result in this file, not just once per bug.

## Iterations That Didn't Work

- **A new `menuDisabled`/`menu-disabled` property and attribute on `auro-menuoption`, set by the menu.** The first design considered giving `auro-menuoption` a second, menu-owned disabled-like flag (reflected attribute, consumed by `isOptionInteractive()`, `handleClick()`, the `isActive` getter, and CSS), so the menu could mark options inert without ever writing to their own `disabled`. This was fully planned (including a `menuDisabled` reactive property, aria-disabled handling, and CSS selectors keyed on `[menu-disabled]`) but rejected before implementation: having two disabled-like flags on the same element was judged confusing to maintain and reason about, and unnecessary — the menu-level guards plus CSS-only visual treatment achieve the same behavior without adding any new public or private surface to `auro-menuoption` at all.
- **Propagating `disabled` down to nested `<auro-menu>` instances**, mirroring how `noCheckmark`/`size`/`shape` already propagate via the existing `querySelectorAll('auro-menu, [auro-menu], ...')` pass. Proposed by code review as one of two possible fixes for the nested-submenu gap (see Root Cause/The Fix). Rejected: this would reintroduce the exact mutation bug this ticket fixes, just one level up — an authored `disabled` on a nested submenu would get silently overwritten whenever an ancestor's `disabled` changed. The ancestor-chain *check* added to `isOptionInteractive()` resolves the same gap by reading state at interaction time instead of writing it ahead of time.
- **Three earlier iterations of the CSS visual treatment in `color-menu.scss` before the shipped version, each over/under-correcting the last:**
  1. *An explicit `::slotted(auro-menuoption)` rule without `!important`* declared the disabled-look custom properties directly on each slotted option. Code review calculated that this local declaration's specificity, `(0,2,2)`, loses to the option's own pre-existing `:host([selected].active)` rule, `(0,3,0)` — so a selected-and-currently-highlighted option would keep its accent background tinted instead of fully graying out while the menu was disabled.
  2. *Switching to plain inheritance from `:host([disabled])` (no `::slotted()` at all)* was the fix attempted for (1) — reasoning that an inherited value can never be out-specificity'd since it never competes on specificity in the first place. True, but it overcorrected: a value that never competes also never *wins* against *any* local declaration, so a merely-`selected` (not even `.active`) option's `:host([selected])` rule — which sets all three color properties — now fully overrode the disabled look on every property, not just the one `(0,2,2)` lost before.
  3. *`::slotted()` with `!important`, but no plain inheritance alongside it* fixed (2)'s selected-option regression by reinstating a local, unconditionally-winning declaration — but a third code-review pass caught that `::slotted()` alone doesn't reach a nested submenu's own options at all (it only matches a host's *direct* slotted children, never through a second shadow-tree boundary), so disabling the root silently stopped visually dimming a nested submenu's options, even though their interactivity was still correctly blocked.

  The version that actually holds for every case this change set out to cover — authored-`disabled`, `selected`, `selected.active`, arbitrary nesting depth, and plain — is **both declarations together** (shipped): plain inheritance on `:host([disabled])` for depth, plus `::slotted()` with `!important` for overriding a direct child's local color. The one remaining known gap (a selected option nested two-plus levels below the disabled one) is accepted rather than chased into a fourth iteration — see Why This Works.
