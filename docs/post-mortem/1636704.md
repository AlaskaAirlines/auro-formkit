# AB#1636704

## Executive Summary

`auro-checkbox-group` had the same accessibility bug as `auro-radio-group` (AB#1344690), plus one more: the "this is invalid" signal for a required checkbox group was placed on the wrong part of the component, wasn't linked to the visible error text, and — worse — didn't reliably appear at all for the single most common invalid case (a required group left empty). This work fixes all three: the invalid signal now lives on the correct part of the component, is always triggered by the group's real validity, and is formally linked to the error message so screen readers can announce both. Ticket: [AB#1636704](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1636704).

## The Problem

When a required checkbox group is submitted with nothing checked, it should tell screen reader users two things: that the group is invalid, and what the error message says. Before this fix, that never happened reliably. The invalid signal was wired to the wrong internal property, so leaving a required group empty produced no invalid indication at all unless the application separately supplied an error message. Even when an error message was supplied, the invalid signal was attached to a part of the component assistive technology doesn't associate with the actual group, and the message had no formal link back to the group.

## Root Cause

- `components/checkbox/src/auro-checkbox-group.js` renders the group's real semantics on a `<fieldset>` inside its shadow DOM, but `aria-invalid` was imperatively set on the *custom element host* in `updated()`, inside `if (changedProperties.has('error'))` — meaning it fired only when the `error` **attribute** changed, never when `validity` changed on its own.
- Because of that, a required-and-empty group (`validity === 'valueMissing'`) never received `aria-invalid` unless the application also set an explicit `error` string — the most common invalid case for this component was invisible to assistive technology.
- The error message rendered inside a versioned `auro-helptext` element with `role="alert" aria-live="assertive"`, which announces once when it appears, but had no `id`, and the fieldset had no `aria-describedby`/`aria-errormessage` pointing at it.
- Individual `auro-checkbox` children received an `error` attribute for styling but no `aria-invalid` of their own.
- A pre-existing, unrelated markup typo was found in the same lines being edited: a stray extra `"` in the error-branch help-text template (`appearance="${...}"" role="alert"`).

## The Fix

- Moved the `aria-invalid` set/remove logic out of the `error`-attribute-triggered block and into the existing `changedProperties.has('validity')` block, alongside the pre-existing per-checkbox `error` attribute propagation — so it now fires for *any* reason `validity` becomes non-`'valid'`, including `valueMissing`.
- Added a declarative `aria-invalid` binding directly on the `<fieldset>` in `render()`, using `ifDefined` so the attribute is present only when `validity` is not `'valid'`.
- Added `this.uniqueId` (via `UniqueId` from `@aurodesignsystem/auro-library`, matching the pattern already used in `base-input.js` and just applied to `auro-radio-group` in AB#1344690), and wired `aria-describedby="${this.uniqueId}"` on the fieldset to `id="${this.uniqueId}"` on the help-text/error element (both render branches).
- Propagated `aria-invalid` to each `auro-checkbox` child in the same `validity`-driven block.
- Fixed the stray extra `"` typo in the error-branch help-text template while already editing that line.
- Updated the four existing WTR tests that asserted `aria-invalid` on the host, and added new tests for: the fieldset-level toggle, the `aria-describedby`/`id` association, a required-and-empty (`valueMissing`) group correctly getting `aria-invalid` (a case that was previously untested and would have failed before this fix), and per-checkbox `aria-invalid` sync.
- Added 5 Playwright accessibility-tree tests (`apps/shared/accessibility-tree.suite.ts`), run against both the React and Svelte framework apps; they are enumerated under "Ticket Completeness" below. (This landed as 4; a fifth, covering focus traversal across options while the group is invalid, was added later in code review.)
- Added two Accessibility-section smoke steps to `components/checkbox/test/MANUAL_TESTING.md`, plus a note documenting the intentional per-checkbox `aria-invalid` redundancy (see Learnings).

## Why This Works

- `role` and `aria-invalid` now live on the same element (the fieldset) for the invalid check, matching the fix already validated in `auro-radio-group`. Unlike the radio group, this fieldset has no explicit `role` attribute — it relies on the native `<fieldset>` element's implicit "group" role, which is the correct semantic for a checkbox group (multiple selections allowed) as opposed to `radiogroup`.
- **Caveat on that last point, recorded after review:** "`group` is the correct grouping role" and "`group` is a role that supports `aria-invalid`" are two different claims, and only the first follows from the reasoning above. On the second: `aria-invalid` is a *global* attribute in ARIA 1.1, applicable to any role; ARIA 1.2 deprecates that global use in favor of a supported-role list that includes `radiogroup` and `checkbox` but **not** `group`. So the radio group's explicit `role="radiogroup"` is unambiguously spec-clean, while this component's implicit `group` role sits in the deprecated-global gap. It was verified rather than assumed: `aria-invalid` is not a *prohibited* attribute for `group`, and axe-core 4.11.4 resolves it as global (`global: true` in its attribute table) and reports **zero** `aria-allowed-attr` / `aria-prohibited-attr` violations against the rendered invalid group in a real browser. Keeping it is therefore a deliberate choice: the alternative — dropping it from the fieldset and relying on per-checkbox `aria-invalid` alone — would be strictly 1.2-pure but would discard the group-level invalid signal the ticket asked for. A permanent axe assertion now pins this outcome in the test suite, so if tooling later honors the 1.2 deprecation it fails in CI rather than in a consumer's audit.
- Tying `aria-invalid` to `validity` instead of `error` closes the actual defect: `validity` is the authoritative state set by the shared `AuroFormValidation` package for *both* `valueMissing` (required-and-empty) and `customError` (the `error` attribute) — `error` alone only ever covered one of those two paths.
- Propagating `aria-invalid` to individual `auro-checkbox` children is safe because `auro-checkbox`'s `role="checkbox"` reflects onto its own host element (confirmed by reading `auro-checkbox.js` before making the change) — so there's no host-vs-shadow-DOM mismatch to repeat, matching the reasoning already used for `auro-radio`.
- Both the fieldset and the help-text element live in the same shadow root, satisfying the ticket's explicit risk callout about shadow-root-scoped `id` association — verified directly in a WTR test that resolves `aria-describedby` to an actual element via `shadowRoot.getElementById`.
- Real VoiceOver testing this session (see Ticket Completeness) confirmed the redundancy risk called out in the ticket — announcing "invalid data" from both the fieldset and the landed-on child on Tab-in — is an acceptable, expected trade-off: it happens once on group entry, and is what keeps the invalid state conveyed on every subsequent move between children, which is the entire reason the per-child `aria-invalid` was added.

## Outcome

The checkbox group's invalid state now reliably appears whenever the group is actually invalid — including the required-and-empty case that previously showed nothing — and is linked to its error message so assistive technology can convey both. As of the latest change on this branch, all 259 tests in the `auro-checkbox` package pass at 99.38% coverage, the five Playwright accessibility tests for this component pass in both the React and Svelte framework apps with zero regressions, and lint is clean on the changed source file (pre-existing, unrelated lint warnings in the test file confirmed unchanged via a baseline comparison).

## Follow-up Fix — Child State Desync

Recorded as its own section rather than folded into Root Cause / The Fix above, because this component's commit message and the follow-up commit both cite line ranges inside those sections and editing them would invalidate immutable references. (Lesson noted in Learnings: cite headings, not line numbers.)

Code review of this branch found the same class of gap that affected `auro-radio-group`, in the milder of its two forms.

**Root cause.** `handleItems()` is wired directly to the default slot's `@slotchange` and ends in an unforced `this.validate()`. If the group is *already* invalid — `valueMissing` or `customError` — that validate call does not *change* `validity`, so the `changedProperties.has('validity')` branch in `updated()` never runs and a newly-slotted `auro-checkbox` received neither `error` nor `aria-invalid`. Unlike the radio group, nothing was actively cleared here (this component's `handleItems()` never touched `error`), so this was a missing-state gap rather than the radio group's worse stale-state one, where a child could render valid while announcing "invalid data."

**The fix.** Both attributes are now written together by a single private method, `syncCheckboxValidity()`, called from both the `updated()` `validity` branch and `handleItems()`. This deliberately matches the shape used in `auro-radio-group` so the two siblings no longer diverge on the same bug.

**Known side effect.** Because `syncCheckboxValidity()` clears `error` when the group is valid, `handleItems()` now removes the `error` attribute from every child on each slot change. An `error` set directly on an individual `auro-checkbox` by a consumer will therefore be cleared by a subsequent slot change. `auro-radio-group` already behaved this way; this aligns checkbox with it rather than introducing a new divergence, but it is a real behavior change for anyone setting `error` per-option instead of on the group.

**Coverage.** A regression test asserts that a checkbox slotted into an already-invalid group receives both attributes; it fails against the pre-fix source. An axe assertion on an invalid group pins the ARIA-attribute outcome discussed in the caveat above.

## Breaking Change Assessment

**Decision: not a breaking change. This ships as `fix` (PATCH) on `dev`.** Recorded explicitly because it is a judgment call rather than a mechanical one, and code review raised it on two separate passes. This matches the assessment recorded for the sibling fix in [`1344690.md`](1344690.md).

What changed observably: `aria-invalid` was previously set imperatively on the `<auro-checkbox-group>` **host** element and is now set on the shadow-DOM `<fieldset>` and on each `auro-checkbox`. The host attribute is never set again. A consumer stylesheet rule such as `auro-checkbox-group[aria-invalid="true"] { … }`, or an end-to-end assertion on `auro-checkbox-group[aria-invalid]`, therefore stops matching silently, with no deprecation window. That cost is real and is the reason this section exists.

A second observable change, from the "Follow-up Fix — Child State Desync" section above, is assessed here rather than left implicit: `syncCheckboxValidity()` clears `error` from every child whenever the group is valid, and it now runs on slot change as well as on `validity` change. An `error` set by a consumer directly on an individual `auro-checkbox` — a documented public attribute of *that* component — is therefore removed on the next slot change. This is treated as non-breaking on narrower grounds than the `aria-invalid` relocation: the pre-change `updated()` validity branch already ran `el.removeAttribute('error')` across all children whenever validity changed (verifiable via `git show 24957eac6:components/checkbox/src/auro-checkbox-group.js`), so the group was already authoritative over per-child `error` and a consumer could never durably hold that state against a group validity change. The change widens *when* the clearing fires; it does not introduce the clearing. `auro-radio-group` behaves identically.

Reasons it is nonetheless treated as non-breaking:

- No public API surface changed. No attribute, property, method, event, or slot was added, removed, renamed, or re-typed. The `validity` property, the `error` attribute, and the visual presentation are all unchanged.
- The host attribute was never documented as public API. The accessibility page described these as `<fieldset>` attributes *before* this change.
- Setting ARIA state on an element that does not carry the corresponding `role` was precisely the defect being fixed. Keeping the host attribute for compatibility would mean keeping the bug.
- Separately, the host placement was *already* not working for the most common invalid case: because the set/remove lived in the `error`-attribute branch, a required-and-empty group (`valueMissing`) never received the attribute at all. Consumers could not have been relying on it for that case, because it was never there.
- The ADO work item explicitly records "Breaking change: None — this corrects accessibility semantics; the public API and visual presentation are unchanged for existing consumers."
- On the per-child `error` clearing specifically: it widens the trigger for behavior the group already owned rather than withdrawing a guarantee consumers had, and the documented way to put a checkbox group into an error state — the group-level `error` attribute — is unaffected.

Mitigation chosen in place of a MAJOR bump: the accessibility page now states that the attribute lives on the internal `<fieldset>` rather than the host, and directs consumers to read the `validity` property.

**Known gap in that mitigation:** unlike `auro-radio-group`, whose fieldset exposes `part="radio-group"`, this component's `<fieldset>` carries no `part` attribute, so it is not reachable from a consumer stylesheet at all. The accessibility page's advice to "query the internal fieldset" is therefore only actionable from within a test that can pierce the shadow root, not from CSS. `validity` is the reliable public hook until a `part` is added — worth a follow-up ticket.

If this assessment is ever rejected, note that the consequence is not only a `BREAKING CHANGE:` footer and a MAJOR bump — repo policy routes intentional breakers to `breaking/formkit-v6` rather than `dev`, so the work would need retargeting.

- **A decision on whether individual `auro-checkbox` elements expose `aria-invalid` is made and reflected in the implementation** — decided yes and implemented, grounded in `auro-checkbox`'s host-level `role`. Now also documented on the accessibility page alongside the ARIA 1.1-global vs. 1.2-deprecated-global analysis for the fieldset's implicit `group` role (see "Why This Works").
- **Screen readers announce both the invalid state and the error message when navigating the group after an invalid entry, verified on at least two AT/browser pairs** — completed on **VoiceOver + Safari** and **VoiceOver + Chrome**, confirming on both that the invalid state *and* the message text are announced on entry, and identifying the "invalid data" ×2 redundancy as an acceptable trade-off rather than a bug. - **New/updated WTR unit tests assert `aria-invalid` placement and that the error-association attributes toggle correctly with validity, and pass** — including a `valueMissing` regression case that fails against the pre-fix source, the slot-change regression, and an axe assertion. Full suite: 259 passing, 99.38% coverage.
- **Playwright interaction/a11y tests cover the invalid-entry flow (focus/keyboard navigation of the group when invalid)** — five tests in `apps/shared/accessibility-tree.suite.ts`, run against both the React and Svelte framework apps: fieldset-not-host placement, the `aria-describedby` association, per-checkbox `aria-invalid` when invalid, removal of `aria-invalid` when the group becomes valid, and retention of `aria-invalid` as focus moves between options. The last two close gaps found in code review — see the note below.
- **`components/checkbox/test/MANUAL_TESTING.md` gains steps in its `auro-checkbox-group` Accessibility section verifying the invalid state is announced and the error message is associated with the group** — added, with a note on the expected dual-announcement behavior.

**On the "keyboard navigation" half of the Playwright item.** The first pass satisfied only the *focus* half — invalidity was triggered through a real focus/blur cycle, but no test moved focus between checkboxes while the group was invalid, which is the single behavior the per-checkbox mirroring exists to guarantee. Code review surfaced this and it is now closed by `every checkbox keeps aria-invalid as focus moves between options while invalid`, which invalidates the group, then focuses each option in turn and asserts every one exposes `aria-invalid="true"`. Checkboxes are Tab-navigated rather than arrow-navigated, so this moves focus directly rather than using arrow keys as the radio equivalent does.

Separately, the paired removal test previously asserted the attribute was absent on a fresh page, where it had never been set — it confirmed "never added" rather than "gets removed." It now drives the group invalid, asserts `aria-invalid="true"`, then checks an option and asserts the attribute is gone from both the child and the fieldset, so the removal path is genuinely exercised in a real browser.

**Risk that materialized:** the Risks section warned that "removing/adding `aria-invalid` must stay in sync with the existing `error`-attribute propagation to child checkboxes so state doesn't diverge." That is exactly the defect the follow-up fix above addresses — the ticket predicted it, and it still shipped in the first pass and had to be caught in code review. See [Follow-up Fix](#follow-up-fix--child-state-desync).

## Learnings

- `aria-invalid` must be tied to the property that actually represents "is this invalid," not to whichever attribute happens to be adjacent in the code. This component had it tied to `error` (one specific *cause* of invalidity) instead of `validity` (the authoritative state covering all causes) — the bug was invisible in the common case precisely because `error` and `validity` usually change together, except when `required` validation alone drives `validity` to `valueMissing`.
- When fixing an ARIA-placement bug in one component, check sibling/analogous components immediately — this exact bug (and a variant of it) existed in `auro-checkbox-group` alongside the one reported in `auro-radio-group`, found by deliberately checking for the same shape of mistake rather than waiting for a separate report.
- A component's `role` doesn't have to be explicit to be correct — `auro-checkbox-group`'s fieldset has no `role` attribute at all and is still correctly exposed as a group via the native `<fieldset>` element's implicit role, unlike `auro-radio-group` which needs an explicit `role="radiogroup"` override.
- Verified via real AT testing this session: marking both a group and its individual items as invalid causes an expected, documented redundancy (a doubled "invalid data" announcement on initial Tab-in) — this is the correct trade-off, not a bug, because it's what keeps the invalid state conveyed on every subsequent move between items. This is now documented directly in `MANUAL_TESTING.md` so it isn't mistaken for a regression later.
- Do not cite post-mortem **line numbers** in a commit message. This commit's body pins "lines 11-18" and "lines 19-29", and the follow-up commit pins "line 33", which froze those sections: later sections had to be appended below rather than written where they belong, because a commit message is immutable and any insertion above would silently make it point at the wrong text. Cite the `## Heading` instead — it survives edits.
- A stray, unrelated markup typo (an extra `"` in a template literal) was found and fixed opportunistically while already editing the exact line it was on — worth doing when the fix is a one-character, zero-risk correction directly adjacent to work already in progress, rather than leaving it for a separate pass.
