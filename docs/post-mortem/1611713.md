# Post-Mortem: Some interactive demo examples silently inert on formkit demo pages (AB#1611713)

**Branch:** `jjones/fix/renderJSExamples/AB#1611713`
**Scope:** Demo pages and `apiExamples` JS across `checkbox`, `counter`, `datepicker`, and `dropdown`. Surfaced by the AuroDocsSite → formkit 6 upgrade (AB#1605369).

## What happened

A subset of interactive examples on the formkit demo pages rendered but did nothing. Most demos were fine; the affected ones — specific dismiss/close buttons, `show()`/`hide()` triggers, an error toggle, a reset button — had markup present and styling correct, and nothing in the console complained, so they looked finished when they weren't.

Concretely: across four components (`checkbox`, `counter`, `datepicker`, `dropdown`), nine JS-backed examples were embedded on a page but never called by that page's `initExamples()`, and a few more in `dropdown` were wired but broken by two separate runtime faults. These were a minority of the total example set — the other components audited clean — but they had been latent for a while because nothing exercised the demos.

The AuroDocsSite v6 upgrade is what forced the issue into the light. AuroDocsSite consumes the *built* demo artifacts — `components/*/demo/*.min.js` plus the `.md` files with example HTML inlined at build — and calls each page's `initExamples()` from a React `componentDidMount`. Wiring those calls up (AB#1605369) is what exposed the affected examples. And because the demos live in formkit and ship as built artifacts, **AuroDocsSite could not fix them** — every repair was a formkit source change, rebuild, release, and dependency bump away. The symptom appeared downstream; every lever was upstream.

## How the first hypotheses were wrong

The initial read was "the docs site just isn't calling `initExamples()`." That was true for some pages and a red herring for others.

**Wrong hypothesis #1 — "it's a stale build."** After wiring the examples into each page script, dropdown's `match-width`, `error`, and `hide` were still dead locally. The obvious suspect was an un-rebuilt `*.min.js`. Checking mtimes killed it: a dev watcher had already rebuilt `customize.min.js` and `getting-started.min.js` after the source edits, and the new function names and selectors were present in the minified output. The wiring was live and still broken.

**Wrong hypothesis #2 — "the shared `try` block cascades."** `dropdown/customize.js` calls all its examples in one `try`, so one throw kills every call after it. Plausible, and a real latent hazard — but not the cause here, because the elements were all present and only *some* examples failed.

**The actual causes were two unrelated faults hiding behind identical symptoms:**

- On `dropdown/customize.md`, section-header anchors collided with example element ids. `<auro-header id="error">` and `<auro-header id="matchWidth">` share their ids with the example `<auro-dropdown id="error">` / `id="matchWidth">`. `document.querySelector('#error')` returns the **header** (earlier in the DOM), which has no `.hide()`, so the click handler threw. `fullscreen` worked only by luck — its header id is `fullscreenBreakpoint`, which doesn't collide with its element id `fullscreen`. That coincidence is exactly what made the bug look impossible: "the same code works two lines up."

- On `dropdown/getting-started`, the page never called `initExamples()` at all. Unlike `customize.html` (and the checkbox/radio/input getting-started pages), `getting-started.html` had no inline `initExamples()` call, and `demo-support` does not auto-invoke `data-demo-script`. The page only ever "worked" on AuroDocsSite, where React happened to call it. Its `show()` example was additionally untestable because the demo never registered `auro-input`.

## Root cause

The specific bugs are symptoms. The system produced them because demo wiring is **entirely manual and entirely unverified**, and the invocation contract is **implicit and forked across runtimes**.

1. **No check that embedded examples are wired.** Each page's `initExamples()` must hand-import and hand-call every example function. Nothing — no test, lint, or build step — asserts that "every JS-backed example embedded in a `.md` is imported and called by that page's script." Over ~10 components this drifts silently. This is the source of all nine wiring gaps.

2. **The invocation point is implicit and inconsistent.** `initExamples()` is triggered at least four ways depending on page and runtime: an inline `<script>` in the page `.html`, a self-invoke at the bottom of the page JS (`menu`, `form`), the `data-demo-script` attribute, or a React `componentDidMount` on AuroDocsSite. No single owner of "when does init run" means a page can be correct in one runtime and dead in another, and new pages inherit whichever neighbor was copied.

3. **Failures are silent by design.** Example fns used optional chaining (`btn?.addEventListener`, `dropdown?.hide()`), turning "element not found" into a no-op instead of a throw — which also defeats the retry mechanism, since retry only fires on a caught exception. Combined with no console assertions, a dead demo is indistinguishable from a live one until a human clicks it.

4. **The rendered page has one global `id` namespace shared by doc chrome and example markup.** Example authors pick short, friendly ids (`#error`, `#matchWidth`) that collide with header anchors. Nothing detects duplicate ids in the generated demo page. This also quietly breaks in-page anchor navigation to those headers.

5. **Cross-repo coupling with slow feedback.** AuroDocsSite depends on formkit's built demo artifacts, and there is no integration test spanning the boundary. A defect discovered downstream is a release cycle away from being fixable, which is what turned a version bump into a multi-session, two-repo investigation.

## The fix

Wiring gaps closed (example imported + called inside each page's `initExamples()`):

| Component | Page script | Example(s) wired |
|---|---|---|
| checkbox | `getting-started.js` | `reset-state` |
| counter | `customize.js` | `dropdown-mobile-properties` |
| datepicker | `customize.js` | `error`, `validity` |
| dropdown | `customize.js` | `error`, `match-width`, `appearance-inverse-error` |
| dropdown | `getting-started.js` | `programmatically-show`, `programmatically-hide` |

Runtime faults fixed in dropdown:

- **ID collisions** — gave the example dropdowns unique ids and updated the selectors: `error.html`/`error.js` now use `#errorDropdownExample`; `match-width.html`/`match-width.js` now use `#matchWidthDropdownExample`. Headers keep their anchor ids. This also repairs anchor navigation to those sections.
- **Missing invocation** — `getting-started.html` now imports and calls `initExamples()` after `renderPage`, matching `customize.html`.
- **Missing dependency** — `getting-started.js` now registers `AuroInput` (via `@aurodesignsystem/auro-input`, the same way `form/demo/registerDemoDeps.js` does), so the `show()` example's trigger input is a real component.
- **Silent no-ops** — dropped optional chaining from the five wired dropdown example fns so a missing node throws and the retry loop actually runs (continuing the cleanup started in AB#1605369 on the classic/custom/fullscreen fns).

`menu` was audited and found **correct** — it already uses the robust pattern (an examples array, each fn in its own `try`, retry only the still-pending ones). It should be the template for standardization.

## Why nothing caught it

- **Per-component WTR tests load `src/`, not the demo.** Demos are not under test at all; there is no assertion that an example's listener binds or that a click does anything.
- **The demos "work" in whichever runtime happens to call `initExamples()`.** A page dead locally but alive on AuroDocsSite (or the reverse) passes casual inspection in the runtime someone happens to open.
- **Silent-by-default everything.** Optional chaining swallows missing nodes; empty/absent `catch` swallows throws; no console warning on retry exhaustion. There is no signal to catch.
- **The one reliable signal lives across a repo boundary** and only appears when a human clicks a rendered demo on AuroDocsSite.

## Lessons learned

- **Manual wiring with no verification will always drift.** Nine gaps across four components is not carelessness; it's the expected steady state of a hand-maintained import list with no check. The audit that found them is mechanical (see Receipts) and belongs in CI.
- **A coincidence that makes a bug "work sometimes" is a tell, not a comfort.** `fullscreen` working while `error`/`match-width` failed — identical code — was the strongest clue that the fault was in the *page*, not the example. Chase the difference between the working and broken instance before touching the shared code.
- **Optional chaining in example code is a foot-gun.** It converts "this demo is broken" into "this demo is silent," and it neuters the retry it's paired with. Example fns should let missing nodes throw.
- **Demo element ids share a namespace with doc structure.** Short, human-friendly ids collide with header anchors. Scope example lookups (`closest('auro-*')` or query within the example wrapper) or namespace the ids, and check for duplicate ids at build.
- **One implicit invocation contract per runtime is one too many.** "When does `initExamples()` run" needs a single, documented answer, not four copy-pasted ones.
- **The docs site can only be as correct as the artifacts it consumes.** Without an integration test across the formkit→AuroDocsSite boundary, defects are found late and fixed slowly.

## Defenses to add (follow-ups)

1. **CI audit of demo wiring** — for every component, assert each JS-backed example embedded in a `.md` is imported *and* referenced by the page script it loads. Fail the build on a gap. (Note: check for the function *name* in the script, not a literal `fn(` call — `menu` dispatches through an array and a naive call-check false-flags it.)
2. **Duplicate-id check on the generated demo page** — assert no repeated `id` across headers + inlined examples.
3. **A shared `initDemo(examples[])` helper in `packages/`** — runs each example in its own `try`, retries only the failures, bounded count, and `console.warn`s on exhaustion. Every `initExamples()` delegates to it; retire the per-page copies and one-shot variants.
4. **Headless smoke test of built demos** — load each built page, assert no console errors and that a representative interaction wires (e.g. clicking a dismiss button hides its dropdown). This is the missing formkit→docs integration gate.
5. **Document the demo authoring contract** in CONTRIBUTING: how to add an example so it embeds, gets wired, and runs in both runtimes.
