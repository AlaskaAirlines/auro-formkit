## Executive Summary

Guests paying with a **China UnionPay** card can't currently finish typing their card number: the credit-card field stops at 16 digits, but UnionPay numbers run up to 19. UnionPay is one of the world's largest card networks, so this can block a real purchase.

This work makes the credit-card field recognize UnionPay as its own card brand, accept the full 16–19 digit range, group the digits for easy reading, and show a UnionPay icon — bringing it to parity with the Visa, Mastercard, Amex, Discover, and Diners Club brands the field already supports. The change is additive and backward compatible: every existing card brand keeps behaving exactly as it does today.

## Technical Research Document

This file **is** the TRD / decision record for AB#1551772, published as this GitHub Discussion in the Post Mortems category (and mirrored at `docs/post-mortem/1551772.md`). The ticket recommended a TRD because three things were unknown up front: whether variable-length masking was feasible, how to order detection so UnionPay wins over Discover, and whether a UnionPay icon existed. The research below resolves all three — no separate research spike was required — and the change is now implemented (see Ticket Completeness).

## The Problem

The credit-card field treats every card brand as having a single fixed length, and it caps input at 16 digits by default. China UnionPay cards are variable length and can be up to 19 digits, so a guest entering one physically cannot type their whole number. On top of that, UnionPay cards (which begin with `62`) are currently mislabeled — the field shows them the Discover icon — because the field's Discover rule matches *any* number starting with `6`. The result: UnionPay guests see the wrong brand and can be blocked from completing checkout.

## Root Cause

All credit-card behavior lives in two methods in `components/input/src/base-input.js` and one render path in `components/input/src/auro-input.js`. Three design assumptions there prevent UnionPay support:

1. **A single fixed length per brand.** `matchInputValueToCreditCard()` (base-input.js:1257) defines a `creditCardTypes` array where each brand carries one `formatLength` (the *masked-string* character count — Visa's `19` = 16 digits + 3 spaces). Validation assumes exactness: `matchInputValueToCreditCard()` sets `this.validationCCLength = type.formatLength` (base-input.js:1349), and `definePattern()` (auro-input.js:460) emits an exact-length pattern `.{max,max}`. There is no notion of an accepted length *range*.

2. **A 16-digit default cap.** `configureDataForType()` (base-input.js:1188) sets `maxLength = 19` (masked chars = 16 digits) for credit-card before any brand is detected.

3. **Discover is a `6` catch-all.** The Discover entry (base-input.js:1325) uses `/^(?<num>6)\d{0}/u` — it matches *every* number starting with `6`, including UnionPay's `62`. Detection keeps the **last** matching entry (the `forEach` at base-input.js:1343 has no `break`), and Discover is currently the last `6*` rule, so `62…` resolves to Discover.

There is no UnionPay entry in the array, and the `cc-unionpay` icon shipped in `@alaskaairux/icons` (payment category) is never referenced.

## The Fix

*(Implemented — three small, localized edits plus WTR tests. No architectural change.)*

1. **Add a UnionPay brand entry** to the `creditCardTypes` array in `matchInputValueToCreditCard()` (base-input.js), inserted **after** the Discover entry so last-match-wins gives it precedence:

   ```js
   {
     name: 'China UnionPay',
     regex: /^(?<num>62|81)\d{0}/u,
     formatMinLength: 19,   // masked chars at 16 digits (4-4-4-4)
     formatLength: 23,      // masked chars at 19 digits (4-4-4-4-3)
     errorMessage: CreditCardValidationMessage,
     cardIcon: 'cc-unionpay',
     maskFormat: "0000 0000 0000 0000 000"
   }
   ```

2. **Make `validationCCLength` the *minimum* masked length for variable-length brands** (base-input.js:1349), so 16/17/18-digit UnionPay entries aren't flagged `tooShort`, while every fixed brand is unchanged:

   ```js
   this.validationCCLength = type.formatMinLength && type.formatLength
     ? type.formatMinLength   // variable-length card → min acceptable length
     : type.formatLength;     // fixed-length card → unchanged
   ```

3. **Widen credit-card validation to a range** in `definePattern()` (auro-input.js:460): emit `.{min,max}` when a minimum exists, otherwise the existing exact `.{max,max}`:

   ```js
   const minPatternLength = this.minLength || this.maxLength;
   return `.{${minPatternLength},${this.maxLength}}`;
   ```

**Icon:** no code change — `processCreditCard()` (base-input.js:1242) already assigns `this.inputIconName = creditCard.cardIcon`, and `renderHtmlTypeIcon()` (auro-input.js:626) renders `<auro-icon category="payment" name="…">`. Setting `cardIcon: 'cc-unionpay'` is sufficient; the asset already exists.

**maxLength/minLength:** no change — `processCreditCard()` (base-input.js:1236) already sets `maxLength = formatLength` (23) and `minLength = formatMinLength` (19). The 4-4-4-4-3 mask engine (IMask, `lazy: true`) already accepts any partial length, so a guest may stop at 16–19 digits without being forced to fill the mask.

### Prefix decision: `62` and `81`, not `60`

- **`62`** is the primary UnionPay BIN. Placed after Discover, `62…` now resolves to UnionPay; every other `6*` (`6011`, `64x`, `65x`, `60x`) still matches only Discover and is unchanged.
- **`81`** is used by UnionPay cards issued outside mainland China. It overlaps no existing brand (today `81…` falls through to the generic Default Card), so it is purely additive.
- **`60` is intentionally excluded.** Real Discover cards begin `6011`; matching `60` would reclassify genuine Discover cards as UnionPay. Only `62`/`81` are supported.

## Why This Works

- **Variable length is a masking non-issue.** The field's mask is IMask with `lazy: true` (see `getMaskOptions`); a pattern mask defines the *maximum* and accepts any shorter partial value, so 16, 17, 18, or 19 digits are all valid intermediate states. No mask-engine change is needed — only the *validation* needed widening from exact to a range.
- **Validation is driven by masked-length properties, not the native `pattern`.** In `@aurodesignsystem/form-validation` (`validation.js`), credit-card `tooShort` fires when `value.length < validationCCLength` (validation.js:191) and the length rules compare against `minLength`/`maxLength` (validation.js:71,76) — all masked-character counts. Setting `validationCCLength` to the *minimum* (19 masked chars = 16 digits) makes a 16-digit UnionPay card valid, a 15-digit entry `tooShort`, and `maxLength = 23` caps the top end.
- **Precedence is deterministic.** Detection keeps the last matching entry (base-input.js:1343, no `break`), so placing UnionPay after Discover guarantees `62` wins without touching the Discover rule.
- **The "overlap" corrects a mislabel rather than breaking Discover.** The only Discover-claimed numbers in the `62` space are the `622126–622925` alliance range — physically UnionPay cards running on Discover's network — so showing UnionPay for them is more correct. The field does no BIN validation; the only observable effects are the icon (Discover→UnionPay for `62`) and a *more* permissive max length (16→19 digits), so no previously-enterable card becomes un-enterable.

## Outcome

Guests with a China UnionPay card can enter their full 16–19 digit number, see the correct UnionPay icon, and read their number in familiar grouped blocks — removing a checkout blocker for one of the world's largest card networks. Every other card brand looks and behaves exactly as before; the WTR regression cases confirm Discover and the fixed-length brands are unaffected.

## Learnings

- The credit-card field's `formatLength` is a **masked-string character count**, not a digit count (16 digits = 19 masked chars with 4-4-4-4 grouping). Any length reasoning must be done in masked chars.
- Credit-card validity is **not** driven by the native `pattern` attribute — it runs through `@aurodesignsystem/form-validation` against host properties (`validationCCLength`, `minLength`, `maxLength`). Changing `definePattern()` alone would not have affected validity; `validationCCLength` is the real lever.
- Brand detection is **last-match-wins with no `break`** — ordering is the precedence mechanism. More-specific rules must come after broader ones (this is also why `Alaska Airlines Visa` sits after `Visa`).
- A "TRD recommended" flag on a ticket can often be satisfied by a focused research spike whose findings collapse the unknowns — here the spike showed the change was three small, localized edits, not the non-trivial effort the ticket anticipated.
- The `cc-unionpay` icon already shipped in `@alaskaairux/icons`, which retired the ticket's biggest unknown (a possible missing-icon fallback) before any code was written — worth checking the asset library early when a ticket flags an icon as uncertain.
