# AB#1634231

## Executive Summary

The passenger-quantity control (a group of plus/minus counters shown inside a dropdown panel) was closing its panel every time someone tapped a plus or minus button once a counter reached its limit. People commonly use this control to set several quantities at once — for example, choosing how many adults, children, and infants are traveling — so a panel that snapped shut mid-adjustment forced them to reopen it repeatedly and made the control feel broken.

This change keeps the panel open while people adjust counters. The panel now closes only when it should: when the person clicks outside it, presses Escape, or moves focus away. As a related polish item surfaced during the work, the on-screen focus indicator now stays visibly on the counter after a button is pressed, instead of disappearing.

Ticket: [AB#1634231](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1634231)

## The Problem

When a counter group is presented as a dropdown, opening the panel and pressing a counter's minus (or plus) button could unexpectedly close the whole panel. It happened specifically when the button being pressed reached its limit — for instance, decreasing a value all the way down to its minimum. At that moment the button becomes unavailable, and the panel treated that as "the person is done" and closed itself. The result interrupted people before they had finished setting their quantities.

A second, related annoyance: after pressing a counter button with the mouse, the visible focus indicator vanished instead of resting on the counter, so it wasn't clear where keyboard control would resume.

## Root Cause

Two independent mechanisms in the `auro-counter` package combined to produce the behavior.

1. **Dropdown auto-close in `auro-counter-group.js`.** The dropdown suppresses its built-in "close on focus loss" logic (`noHideOnThisFocusLoss = true`, needed because the counters are slotted through several nested shadow roots) and re-implements closing via a `focusout` listener added in `firstUpdated()`. That handler kept the panel open only when `event.relatedTarget` was an element contained by the group. When a counter's plus/minus button reaches an extreme, it is set to `disabled` immediately after the click; the browser then blurs the now-disabled button and fires `focusout` with a **null** `relatedTarget`. Null failed the "contained" check, so the handler called `hideBib()` and the panel closed — a side effect of using the counters rather than a real focus exit.

2. **Focus loss in `auro-counter.js`.** The +/- controls are internal `auro-counter-button` elements with `tabindex="-1"`; the real focusable element for the composite widget is the `[part="counterControl"]` container (`role="spinbutton"`, `tabindex="0"`). A pointer click focuses the button itself. When the click drove the value to a limit and the button became `disabled`, focus was dropped to the document body, so the visible focus indicator disappeared.

## The Fix

**`auro-counter.js` — move focus off the button before it can disable.** Button clicks now route through a new `handleControlClick(action)` that first calls `focusControl()` and then performs `increment`/`decrement`. `focusControl()` focuses the `[part="counterControl"]` container using `focus({ focusVisible: true })`. Because focus is on the container *before* the value change disables the button, focus is never sitting on the button when it disables, so it can't be dropped. This alone prevents the panel-close bug: the disabling button never blurs a focused element, so no null-`relatedTarget` `focusout` is produced inside the group.

**`styles/style.scss` and `styles/color.scss` — key the focus ring on `:focus-within`.** The counter's outline on `:host::part(counterControl)` is now driven by `:focus-within` instead of `:focus-visible`, so the ring renders whenever focus is anywhere inside the control — the `[part="counterControl"]` container itself *or* one of its internal `tabindex="-1"` +/- buttons — rather than only when the container matches `:focus-visible`. Combined with `focusControl()` moving focus to the container after a pointer click, the counter shows a stable, visible focus ring throughout the interaction.

**`auro-counter-group.js` — the panel-close handler stays a simple containment check.** Because the counter-level fix guarantees the button is never the focused element at the instant it disables, the disabling blur with a null `relatedTarget` no longer occurs, and the group's `focusout` handler needs no special-casing. It keeps the panel open when `relatedTarget` is an element inside the group and closes otherwise (Tab to an outside element, or an outside click).

An earlier iteration on this branch added a capture-phase document `pointerdown` listener plus a `pointerdownInsideGroup` flag (and a `disconnectedCallback` to unregister it) to distinguish a control-click blur from a real exit. That machinery was **removed** once the counter-level reordering made it unnecessary — the fix now lives entirely at the source (focus-before-disable) plus the CSS ring change, leaving the group handler as the original, simpler containment check.

## Why This Works

- **Ordering restores the invariant.** The disabling of a control button is a consequence of the value change. Performing the focus move first guarantees the button is unfocused at the instant it becomes `disabled`, so the browser has no focused-then-disabled element to blur. This is more robust than reacting to the blur after the fact.
- **A single fix at the source beats a downstream guard.** Because focus is moved off the button before it disables, no null-`relatedTarget` blur is ever produced inside the group. The group's `focusout` handler can stay the simple, original "is `relatedTarget` inside me?" check — there is no ambiguous focus-loss case left for it to disambiguate, so the `pointerdown` tracking is not needed.
- **Outside click, Escape, and Tab still close.** A Tab-away yields a `relatedTarget` outside the group and an outside click yields a null `relatedTarget` — both fail the containment check, so the handler closes the panel; Escape closing is untouched.
- **The correct counter shows focus.** Verified with real pointer clicks (`sendMouse`) that `shadowRoot.activeElement` is the clicked counter's own `[part="counterControl"]` and that it matches `:focus-visible` — including when the click drives the value to min or max. The `:focus-within` ring keeps the outline visible whether focus lands on the container or an internal button.

## Outcome

Adjusting quantities in the dropdown now works the way people expect: pressing plus or minus changes the value and the panel stays open, even when a counter hits its minimum or maximum. The panel closes only on a click outside it, the Escape key, or moving focus away. The focus indicator remains visible on the counter after a button press. The counter component's full test suite passes (293 tests, 100% coverage); the reported scenario is covered end-to-end by a real-pointer (`sendMouse`) regression test, and the tests that exercised the removed `pointerdownInsideGroup` machinery were dropped along with it.

## Learnings

- A control that becomes `disabled` while focused causes the browser to blur it with a **null** `relatedTarget`. Any "close on focus loss" logic keyed on `relatedTarget` containment will misfire when an interactive element disables itself — so it is better to prevent the element from being focused-then-disabled than to teach the handler about the null case.
- Move focus to a stable owner **before** disabling the element that has it. Reordering the focus move ahead of the state change prevents the focus-loss entirely — cleaner than detecting and repairing it afterward, and it let us delete a whole downstream guard.
- Prefer fixing an ambiguous focus-loss at its source over adding a discriminator downstream. A capture-phase `pointerdown` guard (`composedPath().includes(host)`) is a reliable, timing-independent way to tell "did this interaction start inside my subtree?" — but here the source fix removed the ambiguity outright, so the extra listener, `disconnectedCallback`, and flag bookkeeping were net complexity and were removed.
- `document.activeElement` is a poor discriminator during focus churn: it can transiently be `<body>`, and after a panel closes it reflects the restored trigger focus — so it can look "inside" for the wrong reason. Don't gate close/keep decisions on it.
- Programmatic `focus()` after a mouse interaction does not match `:focus-visible`. Use `focus({ focusVisible: true })` and/or key the ring on `:focus-within` so the outline renders whenever focus is within the control, regardless of how it got there.
- Composite widgets (here, a `role="spinbutton"` container wrapping `tabindex="-1"` buttons) should keep focus on the single focusable container; internal controls should not become the resting focus target.

## Iterations That Didn't Work

- **`focusout` guard keyed only on `relatedTarget` containment.** The original handler kept the panel open only when `relatedTarget` was contained. It missed the disabling-button case because that blur reports a null `relatedTarget`, so the panel still closed.
- **Deferred re-check of `document.activeElement` (requestAnimationFrame).** Attempted to close on a null `relatedTarget` only if, one frame later, focus had left the group. It failed both ways: at the animation frame focus was transiently on `<body>` (so it closed when it shouldn't), and the group only *appears* focused afterward because closing returns focus to the trigger — making `activeElement` an unreliable discriminator. A reproduction test confirmed the panel still closed.
- **Redirecting focus to the container *after* performing the value change.** This kept the panel open and restored focus, but relied on the button's disable being asynchronous. It was reordered to move focus *before* the value change so the button is never focused at the moment it disables.
- **Focusing the control without `focusVisible: true`.** Focus landed on the correct counter container, but because the interaction was a mouse click the `:focus-visible` ring did not render, so the focus indicator was still not visible. Adding `focus({ focusVisible: true })` — and later moving the ring to `:focus-within` — resolved it.
- **Group-level `pointerdown` tracking to distinguish a control-click blur from a real exit.** A capture-phase document `pointerdown` listener recorded whether the interaction began inside the group (`pointerdownInsideGroup`), and the `focusout` handler kept the panel open on a null `relatedTarget` when it had. It worked, but it was a downstream guard for a focus-loss that the counter-level fix prevents outright — and it carried a document listener, a `disconnectedCallback`, reconnect re-registration, and flag-reset bookkeeping. Once `handleControlClick` moved focus before the disable, the null-`relatedTarget` blur stopped happening, so the whole mechanism was removed in favor of the simpler source fix plus the `:focus-within` ring.
